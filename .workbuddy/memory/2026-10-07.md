## 强力塔改为真·范围攻击（AOE / §Z.10）

用户要求："修改强力塔的逻辑，它是 AOE，也就是范围攻击的效果，不是单体攻击。"

- **现状缺陷**：强力塔（`TowerType.Aoe=2`，id 4/5/6）配的是 id=2 爆炸弹（`aoeRadius=1.2`），
  `OnHit` 里也确实有溅射逻辑 —— **但弹体必须先"追尾撞上"某只怪才触发**。
  于是表现为"单体攻击 + 一点溅射"：目标提前死亡/走位躲开就完全空放，溅射永不发生。
- **新实现**：AOE 弹飞向**发射瞬间锁定的落点**（`_aoeTargetPos`），到达即引爆，**不追尾**
  - `BaseBullet.Init`：`_isAoe = _aoeRadius > 0`；快照 `_aoeTargetPos = target.Position`；朝落点定向
  - `BaseBullet.Tick`：AOE 支路 —— 位移前判到达、位移后判到达/越点，到达即 `Explode(落点)`；
    超时（lifeTime）就地引爆而非静默回收
  - `BaseBullet.Explode(center)`：把原 `OnHit` 内联的溅射循环抽出复用，对落点半径内**全部**存活敌人造成伤害
  - `OnHit` 里若 AOE 弹撞到怪，也走 `Explode` 兜底
  - `TowerConfig.IsAoe`（按 `TowerType.Aoe`，与 `IsSlowAura` 同口径）
- **关键决策**：
  1. **落点发射瞬间快照、之后不可变** —— 跟着目标走就退化成追踪弹
  2. **到达即炸，不看落点上有没有怪** —— 伤害范围从落点算，这是范围攻击与单体攻击的本质分界
  3. **越点判定（`Dot(dir, 落点-当前位置) ≤ 0`）+ ε=0.08** —— 防高速弹 + 大 dt 一帧跨过落点永不判定
  4. **塔侧 `Fire(target)` 签名不变** —— "无目标绝不开火"不变量保留，落点由子弹从 `target.Position` 快照
- **未改动**：TowerInfo 强力塔行（数值本就对）、`aoeRadius`（属平衡）、未加独立爆炸表现
- 配置：`BulletData.xlsx` id=2 的 desc 同步为新口径；Luban 重导通过（`== succ ==`）

## 接入 SQLite + AES 本地数据持久化（M4）

需求：SQLite 集成/初始化、统一 CRUD 封装、AES 加密敏感数据且密钥不硬编码、接入所有本地保存场景、数据层与业务层解耦。

### 关键技术选型（★ 结论要记住）

- **SQLite 用 P/Invoke 直连原生库，不引入 Mono.Data.Sqlite / sqlite-net**：
  `Mono.Data.Sqlite.dll` 在 Unity 2022 不再自动引用，手工放 Plugins 且 Android/iOS 还要带原生库，
  漏一个就"整个工程编译不过"；sqlite-net 是 4000+ 行第三方单文件。
- **Windows 用 `winsqlite3.dll`（系统自带，实测 3.43.2，导出符号齐全）→ 零二进制依赖**。
  已用 python+ctypes 实测：建表/绑定/查询/事务全通。
  换平台：`SqliteNative.Library`（`__Internal` / `sqlite3`）；若要自带 `sqlite3.dll` 只改 `WindowsLibrary` 一处。
- **必须用一个长连接 + `SQLITE_OPEN_FULLMUTEX` + 托管锁**；绑定字符串用 `SQLITE_TRANSIENT`（否则 GC 后读脏内存）；
  `sqlite3_column_text` 返回的指针不保证 0 结尾，要用 `sqlite3_column_bytes` + 显式长度按 UTF-8 解码
  （用 `PtrToStringAnsi` 中文会乱码）。
- **不加密钥**：主密钥首次运行随机生成，拆两半分别存 `ft_keystore.bin` 与 PlayerPrefs；
  `master=HMAC("...master/v1", A‖B)`，子密钥 `encKey/macKey` 再用 HMAC 打标签派生。

### 分层结构（新增 12 个文件，目录 `Assets/Scripts/Data/Persistence/`）

```
业务/UI → SaveManager(门面，公开 API 一字未改) → ISaveStorage
        → SqliteSaveStorage → IDatabase → SqliteDatabase → P/Invoke → 原生 sqlite3
        → JsonSaveStorage（SQLite 打不开时的回退，且兼容旧明文存档）
  旁路：ICryptoService(AES-256-CBC+HMAC-SHA256, Encrypt-then-MAC) / IKeyProvider / SaveSchema
  组装：SaveStorageFactory（密钥→加密→SQLite→失败降级 JSON）
```

- `DbRow` / `IDatabase`(+`IDbTransaction`+`DatabaseException`) / `SqliteNative` / `SqliteDatabase` / `SqliteTransaction`
  / `CryptoService` / `KeyProvider` / `SaveSchema` / `ISaveStorage` / `SqliteSaveStorage` / `JsonSaveStorage` / `SaveStorageFactory`
- 7 张表：`meta` `player_profile` `level_progress` `game_settings` `level_snapshot` `snapshot_tower` `kv_store`。
  单行表用 `CHECK(id=1)` 强制一行；**加密列用 TEXT 存 Base64 信封**（代价是不能 SQL 排序/聚合 —— 本工程不需要）。
- **回退设计是刻意的**：任一步失败都降级（明文 / JSON），不让环境问题挡住玩家进游戏。
- `SaveManager` 新增公开成员：`BackendName` / `StorageLocation` / `EncryptionEnabled` /
  `TryGetUserValue` / `SetUserValue(key,val,sensitive)` / `DeleteUserValue` / `Flush`。
- `Assets/PopMain.cs` 的 PlayerPrefs 已迁到 `SaveManager` 键值接口（唯一残留在 `Assets/Reporter/` 第三方调试工具，未动）。

## 第二轮：修编译错误 + Android libsqlite3.so + 校验工具链抢修

### 1. 编译错误（用户截图 CS1501）

根因：`CryptoService.Concat` 只接受 3 个 `byte[]`，但信封由「版本+IV+MAC+密文」**4 段**拼成，
调用处传了 4 个实参 —— 这类"实参个数不匹配"只有编译器才报，静态脚本当时查不出来。
修法：改成 `private static byte[] Concat(params byte[][] parts)`。
由此新增 `check_arity.py`（调用实参个数校验），并用故意写错的样本验证它确实能 FAIL。

### 2. Android 原生库（`libsqlite3.so`）

- **结论：必须自带，不能用系统库。** `/system/lib64/libsqlite3.so` 是**平台私有库**，
  targetSdk ≥ 24 时链接器 namespace 拒绝 `dlopen` —— 是**加载失败**，不是版本旧。
- 产物：`Assets/Plugins/Android/libs/{arm64-v8a,armeabi-v7a}/libsqlite3.so`
  （SQLite 官方 amalgamation 3.50.2 + NDK r25c 交叉编译，API 22 对齐 AndroidMinSdkVersion）。
- 走通路径：Zig 0.16 交叉编译**失败**（不再提供 bionic libc）→ 改用 NDK r25c 的 clang 包装脚本；
  NDK 从 `dl.google.com` 下载中断 → 换腾讯云镜像 `mirrors.cloud.tencent.com/AndroidSDK/`。
- 重建脚本：`Tools/build_android_sqlite.sh`（可复现；升版只改 `SQLITE_VER`）。
- **`.meta` 必须手写**（本轮补建，之前漏了）：`Any=0` / `Editor=0` / `Android=1`，
  CPU 分别为 `ARM64` / `ARMv7`。缺 `.meta` → Unity 自动生成默认设置 → 插件可能进不了 APK。
  guid：`4141aed6ac3043caa4106aa6d9fd8304` / `78681d4cfefd4773928c45a688fe8f59`。
- **ARMv7 浮点 ABI 已核**：`e_flags = 0x05000200`（含 `EF_ARM_ABI_FLOAT_SOFT`）= softfp，正确。
  hard-float 会让 `BindDouble` 的 `double` 参数静默错位。
- 两个 ABI 各导出 271 个 `sqlite3_*` 符号，`SqliteNative` 所需 26 个全部为已定义符号。

## 21:10 引入 YooAsset 资源管理系统（3.0.6）

**需求**：给工程引入 Unity 开源资源管理插件 YooAsset。选定：版本 3.0.6（官方 latest / 默认分支 `yoo3`）、
Git URL 直连安装、并写一个 YooAsset 版 `IResLoader` 适配器。

**已核实的事实**（官方仓库 / OpenUPM，不看二手博客——搜索里混了大量 AI 编造的版本号）：
- 包名 `com.tuyoogame.yooasset`，`unity: 2019.4` 起，3.0.6 是 latest；2.x 线最新 2.3.19。
- 依赖 `com.unity.scriptablebuildpipeline 1.21.25` + assetbundle/unitywebrequest 模块，Unity 自动拉取。
- 3.0.x API 与 2.x **不兼容**：`YooAssets.Initialize()` 是**同步 void**（2.x 是 InitializeAsync）；
  包裹初始化走 `InitializePackageAsync(InitializePackageOptions)`；有 `#if YOOASSET_LEGACY_API` 兼容层。
- 收集器默认寻址规则 = `AddressByFileName`（**文件名，去扩展名**）；可用规则只有
  文件名 / 文件夹名_文件名 / 分组名_文件名 / 禁用 —— **没有"完整路径"规则**（我一开始以为有）。
- `AssetHandle` 才是引用计数的载体：**释放句柄 = 资源引用计数归零 → UnloadUnusedAssets 会直接回收**。
- 编辑器菜单：`YooAsset ▸ Bundle Collector / Bundle Builder / Bundle Reporter / Bundle Debugger`。
- 官方 .gitignore 之外的坑：本机 `~/.gitconfig` 有 GitHub 专用代理 `http://127.0.0.1:7890`，
  **代理没开时 UPM 拉包必失败**（沙箱里实测就是这条报错）。

**改动**：
- `Packages/manifest.json`：加 git URL 依赖（`?path=Assets/YooAsset#3.0.6`）。
- **新增** `Assets/Scripts/Core/Res/YooAssetResLoader.cs`（整个文件包在 `#if USE_YOOASSET` 里）。
- `Assets/Scripts/Core/Res/ResLoader.cs`：加 `USE_YOOASSET` 分支（优先级最高）。
- `.workbuddy/tools/check_usings.py` / `check_arity.py`：登记新类型 / 新文件。
- **新增** `Docs/YooAsset_Integration.md`：Unity 侧收尾步骤 + 地址映射原理。

**关键设计决策**：
1. **用编译宏而不是直接替换实现** —— YooAsset 是 UPM 包，拉不下来时只要有 `using YooAsset;`
   就**整个工程编译不过**。加宏后：没宏 = 文件编译为空、工程照常构建；有宏 = 才依赖它。
   与既有 `FORCE_AB` 同一套思路。
2. **地址映射不用改 ResTable / 配置表**：`ResolveLocation()` 按
   「文件名 → ResAddress.Asset → 全路径去扩展名 → 原路径」顺序探测（`IsLocationValid`），命中即缓存。
   收集器用默认规则时第 ① 项必中。
3. **`ReleaseBundle` 只在引用计数真正归零时才释放句柄**（AB 版是无条件清缓存）——
   因为 YooAsset 里释放句柄会让资源当场可被回收，场景还在用就变白。
4. **所有 YooAsset 加载入口都包 try/catch**：它在异常路径上是**抛异常**而不是返回失败句柄，
   而 `Launcher` 的启动回调链没有 try/catch，抛出去就是"启动卡死且看不到原因"。
5. `Preload` 预热用 `typeof(UnityEngine.Object)`（拉物理包是大头成本）；
   与旧实现统一用 `UnityEngine.Object.Instantiate` 而非 YooAsset 的 `InstantiateSync`，保持三套实现行为一致。

**顺带发现（非本次引入的现状）**：`IResLoader.ReleaseBundle` **业务代码零调用**，
`TeardownLevel` 也不调 → 引用计数只增不减，资源常驻内存。AB 实现同样如此，属现状对齐。
若要做"切关回收"，接入点是 `TeardownLevel` 第三段，且三套实现要一起改。

**未能验证**：沙箱内无法编译、也无法驱动 Unity 编辑器。代码正确性靠 7 个静态校验器（全 PASS）+

本机真实代理听在 **`7892`**（`netstat -ano` 查到 PID 36336）。
即代理软件换了端口，配置没跟着改 —— 之前文档里预判的"代理没开"其实是"端口变了"。

**验证手段**（可复用）：
- `netstat -ano | grep LISTENING | grep 127.0.0.1` → 找真实代理端口
- `curl -x http://127.0.0.1:<端口> https://api.github.com` → 返回 `http=200` 即命中
- `git ls-remote --tags https://github.com/tuyoogame/YooAsset.git | grep 3.0.6` → tag 存在
- `curl -x http://127.0.0.1:<端口> https://packages.unity.com/com.unity.scriptablebuildpipeline` → 200，SBP 依赖可取

**改动**：
- 备份 `~/.gitconfig` → `~/.gitconfig.bak-20261007`
- 两条代理项 7890 → 7892（`[http "https://github.com"]` 与 `[https "https://github.com"]`）
- `Docs/YooAsset_Integration.md` 步骤 0 重写为"排查三步 + 四种修法"，附本次真实报错样例
- `MEMORY.md` 代理条目改为"端口漂移"口径 + 排查命令

**结论**：git 与 Unity 包注册表均已连通，用户只需回 Unity 重新解析包即可。
**教训**：这类"写死端口"的代理配置是复发性故障，报错行里的 `proxy 127.0.0.1`（无端口）
就是线索 —— 先验端口，别先怀疑网络。

## 22:30 把 YooAsset 真正接进工程（分包规则 + 宏开关 + 接入向导）

**需求**：包已拉下来，把 YooAsset 的功能落到工程里。两个选定口径：
① 分包粒度 **对齐现有家族分包**（不改变既有打包结果）；② 验证做 **向导内置回读校验**。

**新增三个编辑器文件**（都在 `Assets/Editor/YooAsset/`）：
- `FTBundlePackRule.cs`（套宏）自定义打包规则：不是按目录，而是**读 `ResTable.Bundle`**决定每个资源进哪个包，
  输出与既有 `ResBundle` 逐包一致。用 `[DisplayName]`，靠 `TypeCache.GetTypesDerivedFrom<IBundlePackRule>` 自动发现，无需注册。
- `FTYooAssetDefine.cs`（**刻意不套宏**）宏开关菜单 + `NamedBuildTarget` 四平台组写入。
- `FTYooAssetSetupWizard.cs`（套宏）四步向导：生成收集器配置 → 静态校验 → 构建 → 运行时回读探针。

**为什么不能用 YooAsset 自带的目录规则**：本工程的分包是**跨目录按玩法语义**的 ——
`enemy_rats` 同时包含 `Prefabs/Enemy/Enemy_Rat.prefab` 和 `_UIAssets/Monsters/Rats/Rat/Rat.png`，
任何"按目录/按文件名前缀"的规则都切不出来。只有读 `ResTable` 才能与 `ABNameSetter` 共用一个真相来源。
规则的未登记资源**三级降级**：同目录已登记兄弟 → 最近的有登记祖先目录 → `misc_<顶层目录>`；
**只有出现 `misc_*` 才是真异常**（其余都是预期内的噪声）。

**关键取舍：收集器必须 `EnableAddressable = false`**
- 一开始想用默认的 `AddressByFileName`，于是统计了六个收集根目录下的重名情况 —— **123 组同名文件**
  （`Bat` / `Bear` / `Controller` …）。打开可寻址会强制"寻址地址全局唯一"，收集阶段直接抛 `Address already exists`。
- 关掉可寻址后，**定位键就是资源路径本身**（`SupportExtensionless=true` 再额外附加一条去扩展名变体），
  与 `ResAddress.EditorPath` 天然对齐 → **ResTable 仍是唯一寻址源，零地址映射、零重名风险**。
  适配器 `BuildLocationCandidates()` 探测的「全路径去扩展名 / 全路径」正好命中这两条。

**主动发现并修掉的适配器 bug**：`CreateInitOptions()` 原先给
`CreateDefaultEditorFileSystemParameters()` 传了 `null`。查 `EditorFileSystem.OnCreate` 源码
（第 213–220 行）确认：**packageRoot 为空会直接抛** `EditorFileSystem package root is null or empty.` ——
即"编辑器一进模拟模式就崩"。改法照官方 Sample：先 `EditorSimulateBuildInvoker.Build(pkg, (int)EBundleType.VirtualAssetBundle)`
拿输出目录，再交给文件系统。核实过该类在**运行时**程序集内（内部反射转发到 `YooAsset.Editor`），运行时脚本引用它安全。

**真实包构建参数上的两处选择**：`EnableSharePackRule = true`（未被收集到的依赖进 `share_*` 而不是被丢弃或重复）、
`BundledCopyOption = ClearAndCopyAll`（只清 `StreamingAssets/yoo`，**旧 `AssetBundles`/`build_info` 不受影响**，
两套产物可并存，回退无成本）。

**为什么宏开关要单独一个文件且不套宏**：向导本身也是套宏的，如果用被宏挡住的代码去开宏，
就会出现"要先有宏才能开宏"的死循环。所以 `FTYooAssetDefine.cs` **不引用任何 YooAsset 类型**。
宏要写四个平台组（Standalone/Android/iOS/WebGL）—— 编译宏是**按平台组**生效的，只写一个不算数。

**验证经验（新增一条通则）**：这次给 `check_usings.py` 加了一批 YooAsset 类型映射后，
需要确认收集器**真的扫到了新目录** `Assets/Editor/YooAsset` —— 做法是把 `check_*` 脚本报出的文件数
与 `find` 的实际计数对齐（本工程共有 89 个 Scripts + 21 个 Editor = 110）。
本工程历史上就栽在"扫 0 个文件却一律 PASS"上，所以**凡新增目录，都要确认扫描计数与实际一致**。
7 个静态校验器（`check_code` / `check_usings` / `check_arity` / `check_members` / `check_unity_api` /
`check_events` / `check_ui_contract`）全部 PASS。

**未能验证**：沙箱内不能编译、不能驱动 Unity 编辑器。代码正确性靠静态校验 + 逐行核对 3.0.6 源码签名。
**Unity 侧仍需用户执行**（步骤见 `Docs/YooAsset_Integration.md`）：菜单启用 `USE_YOOASSET` → 跑向导四步。
