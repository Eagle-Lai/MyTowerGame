### 关键技术事实（本次实测确认）

- `Assets/Scenes/main.unity` 是**空骨架**，仅有 4 个对象：`Camera`(orthographic=1, size=5)、`Canvas`(RenderMode=1 ScreenSpaceCamera, UiScaleMode=1, 1920×1080)、`EventSystem`、`bg`

### v2.0 定案的技术路线

1. **2D 方案 = UGUI(RectTransform + Image) + 正交相机 + ScreenSpaceCamera**，1200×1080 参考分辨率。**不用 SpriteRenderer + 物理世界方案**（理由：CanvasScaler 自动适配、塔预制体已是 RectTransform、RectTransformUtility 天然支持拖拽、图集合批）。
2. **棋盘布局改配置表驱动**（`TBLevelMap.cells` 用 `(list#sep=|),string` 每行一个字符串），**废弃** `StreamingAssets/Map/Map*.txt` ASCII 方案（原 3D 逐字符生成物件的方式在 UGUI 下完全不适用）。
3. **数据与视图分离**：`CellData`(纯数据) + `CellView`(视图) + `Point`(仅 row/col/Center/IsWall)，**移除 v1.0 的 `Point.gameObject`/`transform` 强引用**。
4. **配置表位置**：`D:\FreedomTower\Luaban\Config\Datas\*.xlsx`（源表）→ `gen_code_json.bat` → `Assets/Gen/*.cs` + `Assets/StreamingAssets/json/*.json`。
5. **新增配置表**：`TBBullet`（子弹独立成表，2D 下子弹行为需配置化）、`TBLevel`、`TBLevelMap`、`TBGlobal`（全局参数）。
6. **AB 系统设计**：`IResLoader` 接口 + **编辑器直读实现（AssetDatabase）** + 真 AB 实现（`BundleResLoader`）+ `ResTable`(逻辑名→bundle+asset) + `ABNameSetter`(自动打标) + `BuildAssetBundles.cs`。**关键工程决策：编辑器模拟模式**（否则开发效率灾难）。`Unload(false)` 严禁 `Unload(true)`。
7. **战斗判定去物理**（用户明确要求，低端机性能）：删除 `Targetter` 及全部 Collider/Rigidbody → `EnemyGrid`（均匀网格空间哈希，cellSize=2 格，**未跨格零开销**）+ `CombatSystem`（**全局唯一 `UpdateEvent` 订阅**，固定顺序 SyncEnemyGrid→TickTowers→TickBullets，倒序清理失效引用）+ 索敌节流（有目标零搜索）+ 全程 `sqrMagnitude`。目标：Profiler `Physics/Physics2D` 恒为 0，`CombatSystem.OnUpdate` GC Alloc = 0B。
8. **M0 范围收窄为「单回合闭环」**（用户要求）：读配置→生成棋盘→放 1 塔→出 1 波→索敌开火→命中→死亡给金币/漏怪扣血→回合完成提示。14 项 DoD。美术用**占位素材**。
9. **`EnemyGrid` 设计要点**：`Update(e,pos)` 中先算新 cell key，与旧相同则直接 return（关键优化）；`QueryCircle` 返回候选后由调用方用平方距离精确过滤。
10. **`PathProgress`**（`_pathIndex / _path.Count`）是实现"最危险敌人优先"索敌的基础，修正 v1.0 `GetNearsetTarget()` 返回 `_enemyList[0]` 的语义错误。

### v2.1 定案

**世界空间 2D（SpriteRenderer）承载玩法对象 + UGUI 承载 HUD。**
- 决定性依据：119 个怪物 prefab 是分部件骨骼式（每怪 8 个 SpriteRenderer），转 UGUI 成本高且无收益；而塔只有 1 个 prefab，转 SpriteRenderer 成本≈0
- 附带收益：SpriteRenderer 无 Canvas Rebuild 开销，契合"低端机性能"目标
- 由 `PPU=100` + `orthographicSize=5` 反推：**CellSize = 1 世界单位**，可视 10 世界单位高，建议 **16×9** 棋盘
- 必须设置 `Graphics Settings → Transparency Sort Mode = Custom Axis (0,-1,0)`，否则塔怪无法按 Y 互相遮挡
- `sortingOrder` 约定：格子 0 / 路径箭头 10 / 怪物 200（沿用资源包）/ 塔 300 / 血条与伤害数字 500
- HUD 的 Canvas `RenderMode` 建议从 `ScreenSpaceCamera` 改为 `ScreenSpaceOverlay`
- 坐标：`Camera.main.ScreenToWorldPoint`（**z 取 `-camera.transform.position.z`**）→ `BoardView.WorldToCell`；血条改世界空间 SpriteRenderer（不再 UGUI），伤害数字用世界空间 TMP

### 新增工具：`check_unity_api.py`（把这个错误类别变成可静态检查的）

**做法**：Unity 安装目录里每个托管程序集旁边都有一份**官方 API 文档 XML**：


**四个必须知道的坑**（第一版工具全踩了，误报 60+ 条）：

1. **成员名可能带参数列表**（方法）：`name="M:UnityEditor.AssetDatabase.LoadAssetAtPath(System.String,System.Type)"`

2. **XML 只文档化 Unity 自己的 API，不含 BCL**：`System.IO.File` / `Directory` / `Path` 之类

3. **XML 不含继承信息** → 判定分两级：
   ① 查该类型自身名单 ② 查"该成员名是否存在于任何 Unity 类型上"（视为继承成员）
4. **`Grid.QueryCircle` 里的 `Grid` 是我方属性名**，不是 `UnityEngine.Grid` 类型

   另：`System.IO`、`System.Serializable` 这类**命名空间路径**也要排除

**少数 Unity API 未被 XML 收录**，需显式放行，且必须用"直接对程序集做字符串确证"确认存在，

- `GameObject.FindGameObjectWithTag`

## 编译通过后的运行期故障：StreamingAssets 读不出 TextAsset（第四轮）

### 现象（用户贴的 Console 截图）

```

[Res] 文本资源「tbenemydata」加载失败，多数是文件未被识别为 TextAsset。
  路径：Assets/StreamingAssets/json/tbenemydata.json          ← 但这里读不到

```

**两条日志自相矛盾**，这正是定位的关键线索：
- `LoadAssetAtPath<Object>()` 返回**非 null** → 预加载自检判定"就绪"
- `LoadAssetAtPath<TextAsset>()` 返回 **null** → 读内容失败

### 根因（重要，Unity 冷知识）

**`Assets/StreamingAssets/` 下的文件被 Unity 当作"原始文件"（DefaultAsset）处理，
不会被资源管线导入成 `TextAsset`。**

实测证据（对比两处 `.meta`）：

### 现象

用户截图：地图正常生成（16×9、起点绿、终点红、障碍正确），但
**没有路径箭头、没有 HUD、没有怪物**。

### 诊断过程（值得记住的推理链）

日志里 **没有任何异常**，只有：
```
[Flow] 状态=Loading 关卡=1 回合=0/0     ← F1 自检输出
[Config] 交叉引用自检发现 7 处问题       ← 关卡 2..8 的 mapId 不存在，属预期
```
关键推理：`State` 停在 `Loading` 说明 `InitLevel` 在**设了 Loading 之后、设 Preparing 之前**中断了。
再看哪些日志**没有**出现：
- `[Path]` 0 条 → `PathArrowView.Init` 没被调用
- `[UI]` 0 条 → `UIManager.Open` 没被调用
- `[Board]` 0 条 → 建棋盘正常（地图可见也对上了）
- `[Flow] 关卡 1…就绪` 没出现 → `InitLevel` 没走到结尾
⇒ 中断点落在 `boardView.Build` 之后、`pathArrowView.Init` 之前，
  也就是 **`AStarManager.BuildGrid`**。而它没打任何日志，说明是**抛了异常**。
⇒ 异常为什么看不见？因为它由 `EventDispatcher.TriggerEvent(ConfigLoadedEvent)` 调起，
  而 `EventController` 的 `catch` 是**空操作**。

### 根因（两处语义同时反了）

`AStarWrapper` 插件的约定：
```csharp
if (point.Y < mapHeight - 1) up    = map[point.X, point.Y + 1];
if (point.X < mapWidth  - 1) right = map[point.X + 1, point.Y];
```
⇒ **X = 横轴（列，受 mapWidth 约束）、Y = 纵轴（行，受 mapHeight 约束）**，数组是 `map[X, Y]`。

而 `AStarManager.BuildGrid` 写的是 `new Point[rows, cols]` + `Point(row, col)` → **两个轴都反了**。
后果：`point.X < mapWidth - 1` 实际是 `row < 15`（恒真），于是 `map[row + 1, col]`
在 `row=8` 时越界 → `IndexOutOfRangeException`。

### 修法

- `Map = new Point[MapWidth, MapHeight]`（= `[cols, rows]`）
- `Point p = new Point(c, r)`（X=列、Y=行）；`Map[c, r] = p`
- `Point.Row => Y`、`Point.Col => X`
- `GetPoint(row, col)` → `Map[col, row]`；`ResetAllSearchState` 同步
- 新增"数组维度 vs 声明维度"自检，防止再犯
- `EventController` 5 处 `catch (Exception e) { string.Format(e.Message); }`（**空操作**）
  → 改为 `Debug.LogException(exception)`

1. **9 个源文件是 GBK 编码**（含我覆写过的几个——Write 回写时保留了原编码）。
   GBK 文件里的中文字符串在 Unity 里会变乱码，且让工具无法读写。已全部转成 UTF-8 with BOM。
2. **Combat 心跳刷屏**：每 5 秒一条、空闲期也打，把 Editor.log 刷到 3.7MB，淹没真正的错误。

## 第六轮：管理器被实例化两份（怪物不移动的真因）

### 现象

怪物能生成、能看到，但**不移动、只待在起点**；同时 `回合 1` 一开始就"完成"。

### 诊断（关键线索：日志自相矛盾）

```
[Wave] 回合 1 开始：2 个波次 / 13 只怪 / 时间轴 12.7 秒
[Flow] 回合 1 完成，等待开始回合 2          ← 怪物根本没走完却"完成"了
[Combat] 怪=0(存活0) 塔=0 弹=0               ← 存活数恒为 0
```

推理：回合完成的条件是「全部出生 且 存活数 ≤ 0」。
存活数恒为 0 ⇒ **怪物从未进入 `CombatSystem._enemies`** ⇒ 从未被 tick
（这同时解释了"不动"与"回合秒完成"）。可见怪物确实被创建并激活了。

### 根因：管理器有两份实例

```csharp
// Launcher.cs（错误写法）
private readonly List<IManagerInterface> _managers = new List<IManagerInterface>
{
    new AStarManager(), new PlayerDataManager(), new EnemyManager(), ...   // ← new
};

// BaseManager<T>.Instance 是**懒创建**的
public static T Instance { get { if (instance == null) instance = new T(); return instance; } }
```

于是每个管理器存在两个对象：
- `Launcher` new 出来的那个 → `OnInit` 里订阅了 `UpdateEvent` → **每帧被 tick**
- `.Instance` 那个 → 各处 `RegisterEnemy` / `TryBuild` / `AddGold` 写入的 → **从没被 tick**

`CombatSystem.Instance._enemies` 永远是空的 ⇒ 存活数 0 ⇒ 回合空转完成；
怪物只被创建、从不 `Tick` ⇒ 不动。

**同类隐患（一次性都被这个修复解决）**：
- `BulletManager.Instance._pool` 是 **null**（`OnInit` 跑在另一个对象上）→ 一旦开火就 NRE
- `CombatSystem.RebuildGridFromConfig()` 作用在另一个对象上 → 被 tick 的 Grid 用的是默认 cellSize

### 修法

1. `Launcher` 的管理器列表改用 `.Instance`（7 个全部）
2. `BaseManager<T>` 加**永久防护**：构造函数检测"是否由 Instance 的 getter 构造"，
   否则立刻 `Debug.LogError`（用法：把 `new XxxManager()` 改成 `XxxManager.Instance`）。
   这个检测不会有误报——唯一合法的构造路径就是 getter
3. `CombatSystem.OnInit` / `BulletManager.OnInit` 加幂等保护
   （重复 OnInit 会导致 UpdateEvent 重复订阅 → 每帧 tick 两次）

### 附带：关卡 1 初始生命 10 → 20

每只怪漏掉扣 1~3 血，而第 1 回合就有 13 只怪，10 血根本看不到多回合效果。
已改 `SceneInfo.xlsx` 的 `initialHp`（列 13）并重跑导出。

### 教训（写进注释与指南）

- **懒加载单例 + 手动 new 是危险组合**：两者并存时不会有任何编译期或运行期报错，
  只表现为"逻辑静默不生效"。要么禁止 `new`（本项目的做法，并加运行时检测），
  要么让 `Instance` 在被 new 之后仍然复用同一份。
- 判断"某系统是否真的在跑"，看它**有没有被 tick 的副作用**（存活数、位置变化），
  而不是看"对象有没有被创建"。

## 第七轮：游戏已跑通，修一个崩溃 + 补齐动画事件接收者

### 问题一：ArgumentOutOfRangeException（真崩溃）

堆栈精确指向 `CombatSystem.TickEnemies` 的 `_enemies.RemoveAt(i)`。

**根因**：`e.Tick(dt)` 内部会经由
`MoveAlongPath → OnReachEnd → EnemyManager.RecycleEnemy → CombatSystem.UnregisterEnemy`
把元素从 `_enemies` 删掉（也可能一次删多个）。外层倒序循环持有的 `i` 随即失效，
`RemoveAt(i)` 越界。

**修法**：改成「**快照遍历 + 独立清理趟**」：
1. `_tickSnapshot.AddRange(_enemies)` 后按快照 Tick —— 遍历期间完全不碰 `_enemies`，索引天然安全
2. 再单独一趟清理：统计 `AliveEnemyCount`、同步 `Grid`、移除空引用/已回收项
   （这一趟只做纯数据操作，不调用外部代码，不会引发二次修改）

> 注意：快照遍历里**不能**跳过 `!IsAlive` 的怪 —— 死亡动画播放中的怪需要靠 `Tick` 推进回收倒计时，
> 跳过它们会导致永不回收。只跳过 `IsFullyRecycled`。

### 问题二：动画事件 no receiver

Console 刷 17 条 `'Enemy_Bat' AnimationEvent 'SetHead' on animation 'Death' has no receiver!`

**排查过程**：
- 先搜 `.anim` 的 `m_FunctionName` → 0 条（**字段名猜错了**）
- 换成直接搜 `SetHead` → 命中 57 个动画文件

**语义从参数直接读出来**（`_Common/Animations/*/Attack.anim`、`Death.anim`）：
- `SetHead(int)`：0=正常头、1=愤怒头、2=死亡头；攻击动画按 0→1→0 切，死亡动画切 2
- `Event(string)`：形如 "Attack" 的通用钩子（原包用作音效/特效触发点）

**结论：这是美术包留的钩子，但没随包提供接收脚本。** 统计 120 张图集：

用户反馈"血条位置还是错"。查日志发现 **`M0SetupWizard.cs` 有 4 个编译错误**（CS0106/CS1022）：
- `error CS0106: The modifier 'private' is not valid for this item`（行 436/512）
- `error CS1022: Type or namespace definition, or end-of-file expected`（行 545/546）

**后果**：Editor 程序集编译失败 → 我上一轮写的 `MeasureBodyBounds`（血条定位修复）
**根本没有生效**。用户重跑了"9. 导入全部怪物"，跑的是旧代码。

**为什么我的静态校验没抓到**：`check_code.py` 只检查**括号是否平衡**。
文件里多一个 `{`、末尾多一个 `}` 相互抵消，整体依然平衡，
但方法声明会落到类外 —— 这只有编译期才暴露。
**已给工具加上"嵌套层级检查"**：类型/方法声明必须出现在一致的深度上
（namespace=1、class=2、类成员=2），深度不一致就报。

（当前磁盘上的 `M0SetupWizard.cs` 结构已验证正确：成员深度全部为 [2]。）

### 血条问题的真正规律（这次是量出来的，不是猜的）

实测 119 个怪物的显示宽度：**0.58 ~ 4.72 世界单位（差 8 倍）**。
而我原来的规则是"本地宽度 × 0.5，钳制到 0.6~2.5"——
结果**大怪的血条相对过小、小怪相对过大**，视觉上就是"大多数对、有些错"。

**修法**：血条尺寸/位置完全按怪物自身的世界尺寸比例计算，再换算回根节点本地：
- 血条世界宽 = `clamp(worldW × 0.6, 0.4, 4.0)`
- 血条世界高 = 宽 × 0.2（贴图 100×20）
- 顶部 = `bounds.max.y + worldH × 0.18`（间距也按体型缩放，不再是固定 0.3）

（用 Python 解析 prefab YAML 量过：只有 2/119 存在"未激活的最高渲染器"，
所以上一轮的"排除未激活"修复方向没错，但不是主因；主因是尺寸比例。）

### 朝向问题：不再猜，做成可切换

逻辑上 `artFaceLeft=1`（美术默认朝左）→ 向右移动才翻转，是对的；
但用户实测仍不对 ⇒ **我对美术朝向的推断（依据节点名 Head 的位置）反了**。
节点名/节点位置不能代表精灵的朝向。

**修法**：新增 `F3` 运行时切换 `BaseEnemy.ArtFaceLeftOverride`（`bool?`），
对场上所有怪立刻生效，Console 会提示该把 `Global.artFaceLeft` 改成什么值。
一次迭代就能确定正确值，再回填配置表。

### 教训

1. **"括号平衡"≠"结构正确"**。检查代码结构必须验证嵌套层级，否则 CS0106 这类错误会漏。
2. **Editor 工具的修改必须确认 Editor 程序集编译通过**——它和运行时程序集是分开编译的，
   运行时编译成功不代表工具代码生效。
3. **无法从代码推断的美术事实，做成可切换的调试开关**，一次迭代确定，比反复猜测快。

## 第十二轮：血条改小 + 朝向问题的"症状学"判断

### 用户反馈

1. 血条位置基本正确了 ✓（InverseTransformPoint 修复生效），但**血条太大，不搭**
2. 朝向仍不对，且关键描述："**所有**怪物的朝向都是默认向左的"

### 朝向：从症状推断，而不是再改逻辑

"**所有**怪物都朝左" ⇒ **翻转从未发生**（若翻转发生了，向右走的怪应朝右）。

最可能的原因：**用户按了我上轮加的 F3**。F3 的实现是切换 `ArtFaceLeftOverride`，
按一次就变成 `false` → 从此向右移动不再翻转 → 所有怪保持默认朝左
—— 与反馈完全吻合。

**处置**：
- **移除 F3 与 `ArtFaceLeftOverride`**（消除混淆源；调试开关反而制造了新问题）

- **加一条一次性诊断日志**：首次向右移动时打印
  `[朝向] 首次向右移动：artFaceLeft=True → 翻转=True，scale.x=-0.50`
  并说明判定标准："此时怪物头应朝右（终点方向）"。
  这样日志与画面一一对应：日志说翻转了、画面也朝右 → 正确；
  日志说翻转了、画面仍朝左 → 美术默认朝向其实是"右"，把 `artFaceLeft` 改 0 即可。

### 血条大小

- 宽度比例 0.6 → **0.5**，上限 4.0 → **2.2**（0.6 时大怪的血条几乎横跨屏幕）
- **高度改为固定世界值 0.11**（不再跟随宽度）：原来高度=宽度的 1/5，
  大怪的血条高得像一块板，视觉突兀。固定成薄条后所有怪物观感一致
- 宽/高分开定标：`localScale = (barWorldW/sx, BarWorldHeight/(sy×0.2), 1)`

**调试开关本身可能成为新的问题源**。加 F3 的本意是"一次迭代确定朝向"，

调试开关要么放在明确的设置界面里，要么用完即删——不要留在游戏里等用户按。

## 第十三轮：朝向问题的最终结论（靠诊断日志实证）

### 诊断日志给出决定性证据

```
[朝向] 首次向右移动：artFaceLeft(默认朝左)=True → 翻转=True，scale.x=-0.20

```

用户反馈：**仍然不匹配**。

**推理链**（这次是实证，不是推断）：

- 用户看到画面仍朝错方向 ⇒ 镜像后的状态 = 朝左
- 镜像后朝左 ⇒ **原始（未镜像）朝向 = 朝右**

⇒ **结论：本美术包的怪物默认朝右**。之前"默认朝左"的判断
（依据 Rig 里 Head 节点在 -X）是反的——节点位置不能代表精灵的绘制朝向。

（这样以后不会再被"节点名"误导）。

同时**移除了 F3 调试开关**（它本身就是上一轮朝向"看起来更糟"的原因：
用户按一次就把覆盖值设成 false，于是翻转彻底不发生 → "所有怪都朝左"）。

### 附带：清掉 20 条 "The referenced script (Unknown) is missing!"

截图里每次实例化怪物都刷这条。原因：**美术包预制体上带着一个脚本引用，
但那个脚本从来没进过这个项目** —— 正是原本应该接收动画事件的那只脚本
（这也是之前 "AnimationEvent has no receiver" 的根源）。

**修法**：`MonsterPrefabBuilder` 在克隆后调用
`UnityEditor.GameObjectUtility.RemoveMonoBehavioursWithMissingScript(clone)`
把缺失脚本引用清掉（已确认该 API 存在于 UnityEditor.dll）。

### 教训

- **"节点名/节点位置"不能代表精灵的绘制朝向**。视觉事实必须靠运行时观测 +
  日志对照来确定，做成可配置项（`artFaceLeft`）是对的，只是初值猜错了。
- **诊断日志的价值在这一轮兑现了**：一条"翻转已发生 + scale.x 值"的日志，

## 第十四轮：朝向问题的真正解法（原来跟 artFaceLeft 无关）

### 决定性证据：路径形状 + 用户截图

日志里 `DescribeCurrentPath` 打出的路径：
```
(0,0)→(1,0)→…→(8,0)→(8,1)→…→(8,15)
```
即 **先沿第 0 列向下 8 格，再向右 15 格**（纯纵向开头）。

用户截图：怪物在第 0 列**向下走、面朝左**。

### 推理

侧视精灵在**纯纵向移动时不能翻转**（翻了会上下颠倒），所以我的
`FaceMoveDirection` 在 `_lastDir.x ≈ 0` 时刻意不动作 ——
结果怪物在纵向段一直保持**美术默认朝向（朝左）**。

⇒ 玩家看到的"朝向与运动方向不匹配"是**纵向段**造成的，
**与 artFaceLeft 取 0 还是 1 完全无关** —— 这就是为什么前两轮改配置都没用。
（也解释了为什么时对时错：横向段是对的，纵向段是错的。）

### 修法（两处）

1. **`BaseEnemy.SetPath` 增加初始朝向**：沿路径向前找第一段横向移动，
   让怪物**出生时就面朝那个方向**。本工程即"面朝右"——
   于是纵向下降段面朝右、转弯后仍朝右，全程观感一致。
2. **`Global.artFaceLeft` 恢复为 1**：截图证实无翻转时怪物面朝左
   （artFaceLeft=0 时纵向段仍面朝左 ⇒ 原生朝左），上一轮改 0 是被误导了。

### 教训（这一条最值钱）

**当"部分情况对、部分情况错"时，要找的不是某个参数，而是"哪种情况没被处理"。**
三轮里我一直在调 artFaceLeft（0↔1），却没意识到横向段从来都是对的、
错的只是纵向段 —— 而纵向段是"侧视精灵不能翻转"这个**设计约束**导致的，
参数永远修不了它，必须补一个"初始朝向"逻辑。

**另一条**：让用户提供**截图/具体场景**（什么方向、第几格），
比让他说"对/不对"信息量大得多。这次的截图直接暴露了"纵向段"这个关键事实。

## 第十五轮：炮管朝向偏 90°（贴图原生朝向没算进去）

### 现象

塔开火时炮管不指向怪物，子弹方向与炮筒不一致。

### 定位方式（又是"量出来"的）

1. 代码：`_barrel.localEulerAngles.z = Atan2(bd.y,bd.x)*Rad2Deg` → 0°=右，
   即假设"贴图原生朝向是 +X"
2. **把炮管贴图降采样成 ASCII 图看形状**：
   ```
   turret_barrel_128:  上窄下宽的一条，位于图像上半部，枪口朝上
   turret_base_128:    X 形底座，中心对称
   ```
   ⇒ 炮管**原生朝向是 90°（上）**，不是 0°
3. 于是实际指向 = 目标角 + 90°，永远偏 90°

**修法**：加常数 `BarrelNativeAngle = 90f`，旋转角改为
`Atan2(y,x)*Rad2Deg - BarrelNativeAngle`。
换炮管美术时若朝向不对，只改这一个常数。

### 教训

**美术贴图的"朝向"是一种视觉事实，必须看图**。和怪物朝向那轮的教训一致：
节点名、节点位置、代码假设都不能代替"看图"。
把贴图降采样成 ASCII 是个很有效的手段（不用打开图像编辑器，在终端里就能看）。

## 第十六轮：子弹出膛点错 90°（和炮管朝向是同一根因的两面）

### 现象

子弹出现的位置不在炮筒末端。

### 根因

`TowerPrefabConverter` 生成 `BarrelPoint` 时放在 `localPosition = (MuzzleOffset, 0, 0)`，
即**本地 +X** —— 写这段代码时假设"炮管贴图朝 +X"。
但上一轮已用 ASCII 图确认**炮管贴图是竖着画的、枪口朝上（本地 +Y）**。

所以出膛点在炮管的侧面，与炮管指向差 90°。
**这与 `BaseTower.BarrelNativeAngle` 是同一根因的两面**：一个是"旋转时该偏多少"，
一个是"出膛点该放在哪"。

**修法**：`BarrelPoint.localPosition = (0, MuzzleOffset, 0)`（本地 +Y）。
`BarrelPoint` 是 `Img_gun` 的子节点，炮管旋转时它跟着转，所以只要本地位置放对即可。

**同一个"美术朝向"事实会同时影响多处代码**（旋转偏移、出膛点、可能还有弹道起点）。
发现这类事实后，应该**全局搜一遍所有依赖它的代码**，一次改完——
我这次只改了旋转，漏了出膛点，导致多一轮往返。

## 第十一轮：血条偏移的真因 —— 66/119 个预制体根节点带位移

### 用数据定位（而不是猜）

扫描 119 个怪物预制体的根 Transform，得到：
- **旋转：全部 identity**（排除"根节点被旋转"的假设）
- **缩放：119 个全部非均匀**（x ≠ y）
- **位置：66 个 localPosition 不为 0** ← 这就是真因

我的换算是 `topLocal = bounds.max.y / rootScaleY`，**漏掉了减去根节点自身的位移**。
`Renderer.bounds` 是世界空间的，而美术把根节点摆在了一个非零位置，
于是这 66 个怪的血条整体偏移"作者留的偏移量"——偏多少取决于每个怪，所以表现为
"大多数正常、少数怪偏得特别厉害"。

### 修法

用 **`root.transform.InverseTransformPoint(世界点)`** 做换算——一次性正确处理
位移 + 缩放 + 旋转，不再手工除以缩放：

```csharp
float topLocal = rt.InverseTransformPoint(new Vector3(b.center.x, barWorldTop, b.center.z)).y;
float leftLocalX  = rt.InverseTransformPoint(new Vector3(b.min.x, b.center.y, b.center.z)).x;
float rightLocalX = rt.InverseTransformPoint(new Vector3(b.max.x, b.center.y, b.center.z)).x;
float barWidth = Mathf.Abs(rightLocalX - leftLocalX);
```

血条宽度也改用"左右边界的本地距离"（已把非均匀缩放算进去），
而不是 `worldW / sx`。
