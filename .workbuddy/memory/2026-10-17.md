## [家用D] 推送竞态排障（07:15）—— 用户报 TortoiseGit 推送失败、疑需 LFS

- 现象：TortoiseGit 于 2026-10-16 23:23:25 报
  `! [remote rejected] main -> main (cannot lock ref 'refs/heads/main': is at 9caaeb93b… but expected 9284e4edf…)`，
  同批输出 GitHub 大文件警告（`is 85.95 MB`、`GH001`），用户判断"可能需要安装 LFS"。
- 核实（三条独立证据）：
  1. 远端真实值 = 本地 HEAD = **`9caaeb93bacbbb95ca46610b1394a6e11dfb022f`**；`git fetch` 后 `git status -sb` = `## main...origin/main`（无 ahead/behind），工作树干净。
  2. 报错中 GitHub 指认的大文件 blob `12a655185aba6897c468f40744a6e05db9cba701` **就是** `HEAD:Builds/Android/freedomtower.apk`（90,129,604 字节）→ 同一个包早已在远端。
  3. `git ls-remote origin refs/heads/main` 直连复核 = `9caaeb93b`。
- 结论：**不是 LFS 问题，是推送竞态**。22:00 出包后我挂的后台自动重试在 ~23:20 第 9 次推成功并更新了远端 ref；用户的 TortoiseGit 是在"远端仍为 `9284e4edf`"时发起的推送，283 秒把 80 MiB 传完后远端已被推进到 `9caaeb93b`，其携带的旧值对不上 → 服务端拒绝 ref 更新。两者内容零差异，**无需任何修复动作**（那次上传属重复传输，无害）。
- ★踩坑（可复用判据）：`cannot lock ref … is at X but expected Y` 与 GitHub 大文件警告**同时出现**时，先 `git fetch` / `ls-remote` 看远端是否已含该提交，**不要直接去装 git-lfs**；同一分支不要并行推送（两边都会完整上传 80MB，必有一方被拒）。
- LFS 现状：`85.95 MB > 建议上限 50 MB` 只是 warning，GitHub 硬上限 100 MB，本包入库正常。若日后仓库因每版 +86MB 明显变慢，再评估 LFS（需两机均装 git-lfs，且历史重写），当前不必。
