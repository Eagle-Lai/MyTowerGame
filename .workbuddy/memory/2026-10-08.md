## 07:35 排查「启用 YooAsset 后运行没有预期效果」——根因：初始化漏了后两步

**现象**：用户在编辑器里跑项目，效果不对。读 `Editor.log` 拿到真实报错。

**排查路径（从日志入手，不靠猜）**：

1. `grep "error CS"` → 只有 3 行，都在日志第 1045/1052/1055 行（**日志靠前 = 很久以前**）：
   `CryptoService.cs(161,31): error CS1501: No overload for method 'Concat' takes 4 arguments`。
   核对当前源码：`Concat` 是 `private static byte[] Concat(params byte[][] parts)`，
   3 参/4 参调用都合法 → **这是历史遗留、早已修好**，与本次无关。日志是**跨天累积**的
   （开头时间戳 `2026-10-07T06:57`，末尾 Oct 8 07:32），不能只看有没有 `error CS`，要**看行号位置**。
2. `grep "YooAsset\|ResLoader"` → 定位到 185k 行开始的一整片失败。
3. 关键错误：**`Active package manifest not found.`**（18 次）+ `[Res] YooAsset 预加载：0/9 个资源就绪`。
4. 再往上找初始化日志，看到两条决定性线索：
   - `[Res] YooAsset 模式初始化完成。包裹=FreeTower，版本=(未知)，常驻包 3 个`
     —— **版本是 `(未知)`**；
   - 前面还有一条 `YooAssetSettings not found, using default configuration.`。

**根因**（读 YooAsset 3.0.6 源码确认，不是猜）：
**3.0.x 把"初始化"和"加载清单"拆开了。`ResourcePackage.InitializePackageAsync` 只初始化文件系统，
不加载清单**。完整流程必须是三步：

| 步骤 | 调用 | 作用 |
|---|---|---|
| ① | `package.InitializePackageAsync(options)` | 建文件系统 |
| ② | `package.RequestPackageVersionAsync()` | 拿包裹版本号 |
| ③ | `package.LoadPackageManifestAsync(new LoadPackageManifestOptions(version, 60))` | **内部才 `SetActiveManifest`** |

证据链：
- `Runtime/ResourcePackage/Operations/InitializePackageOperation.cs` 的 `InternalUpdate`
  只有 `SetPlayMode → CheckOptions → CreateCore → InitFileSystem → Done` 五步，**没有清单相关步骤**；
- `ResourcePackage.cs:1023` 的 `CheckInitialized` 在 `_fileSystemHost.ActiveManifest == null` 时
  抛 `Active package manifest not found.`；
- `LoadPackageManifestOperation.cs` 在成功分支里调 `_host.SetActiveManifest(...)` —— 唯一激活点；
- `GetPackageVersion()` 读的正是 `ActiveManifest.PackageVersion`，清单没激活就抛 → 所以打成 `(未知)`；
- 官方 Sample 也是三步：`FsmInitializePackage → FsmRequestPackageVersion → FsmUpdatePackageManifest`。

**为什么之前"看起来是对的"**：第一版适配器只写了 ①，日志能正常打印"初始化完成"，
错误全落在业务侧的加载调用上，堆栈指向 `Configs.LoadTable`，**看起来很像是"资源没被收集"**。
再加上向导探针当时也没跑 ②③，所以两边都看不出问题。

**改动**（`Assets/Scripts/Core/Res/YooAssetResLoader.cs`）：

1. `InitCo` 补齐 ②③ 两步，并**把三步的失败信息分开写**（初始化 / 请求版本 / 加载清单），
   不再笼统地报"初始化失败"。
2. **删掉 `InitBlocking` 里那份重复的初始化流程**，改成"把 `InitCo` 泵一遍"（嵌套感知的栈式泵）。
   理由：两份实现必然只改一份 —— 这次就是异步路径缺 ②③。现在只有一份真相。
3. 新增 `WaitStep`（运行态让出帧 / 非运行态 `WaitForCompletion` 推到底）与
   `WaitOpCo`（含 **30 秒超时**）。超时是为了防"驱动器不在场 → 操作永不完成 → 启动卡死且无日志"。
4. `StartRequestVersion` / `StartLoadManifest` 两个入口照旧包 try/catch（YooAsset 异常路径是抛异常）。
5. ① 之前先看 `package.InitializeStatus`：已成功过的直接复用。
   因为 `InitializePackageAsync` 有**重复初始化检测**（抛 `already initialized`），
   而向导探针在同一次编辑器会话里可以被反复点。
   （进 Play 时 YooAsset 会自己通过 `RuntimeInitializeOnLoadMethod(SubsystemRegistration)`
   重置 `s_isInitialized`/`s_driver`/`s_packages`，所以"先跑探针再进 Play"是安全的，

## 07:50 修「点击构建真实资源包报 ErrorCode115」

**现象**（用户贴的控制台截图）：

```
System.InvalidOperationException: [ErrorCode115] Package output directory exists:
  'D:/FreedomTower_1/Bundles/Android/FreeTower/1.0.0'.
  at YooAsset.Editor.TaskPrepare.PrepareOutputDirectory(...)
```
`Build pipeline 'ScriptableBuildPipeline' build failed.` / `Error occurred in build task 'TaskPrepare_SBP'.`

**先确认"第一次其实是成功的"**：`Bundles/Android/FreeTower/1.0.0/` 里已有 30+ 个 `.bundle`
（07:28），`OutputCache/` 里包名是可读的业务名 —— `freetower_config.bundle`、
`freetower_enemy_apes.bundle` …，说明 **`FTBundlePackRule` 的分包完全按设计跑通了**。
`StreamingAssets/yoo/FreeTower/` 也有了首包拷贝，而旧的 `AssetBundles/` + `build_info` 没被动。
所以这不是"配置错了"，而是**同一版本号构建第二次**。

**根因**（读源码确认）：`TaskPrepare.PrepareOutputDirectory` 只要发现
`{BuildOutputRoot}/{平台}/{包裹}/{版本}` 已存在就**直接抛 ErrorCode115**，它不负责清理。
清理是另一条分支：`if (buildParameters.ClearBuildCacheFiles) { PurgeCache(); DeletePackageRootDirectory(); }`，
而 `ClearBuildCacheFiles` 默认 `false`。
⚠️ **YooAsset 官方构建窗口的「清空构建缓存」开关默认也是关的**
（`BundleBuilderSetting.GetPackageClearBuildCache` → `EditorPrefs.GetInt(key, 0) > 0`），
所以在官方窗口里点第二次构建会报一模一样的错 —— 这是 YooAsset 的 UX 坑，不是本工程用法问题。

**改动**（`Assets/Editor/YooAsset/FTYooAssetSetupWizard.cs`）：

1. 新增 `CleanPackageOutputDirectory()`：构建前**只精确删掉本次的版本目录**
   （`param.GetPackageOutputDirectory()`）。输出根在工程根的 `Bundles/`、不在 `Assets/` 下，
   所以不需要 `AssetDatabase.Refresh()`。
2. 新增界面开关「**彻底重建**」（默认关）：勾上才走官方 Sample 的
   `ClearBuildCacheFiles = true`（清 SBP 缓存 + 删整个包裹根目录），并打一条 Warn 说明会更慢。
3. `using System.IO;`。

**为什么默认不直接用 `ClearBuildCacheFiles = true`**（这是本次最关键的取舍）：
它会 `DeletePackageRootDirectory()` 删掉 `Bundles/{平台}/{包裹}` **整个根目录**，
里面包含 **`Simulate`** —— 而 `Simulate` 正是编辑器模拟模式**当前正在用**的清单，
向导第 ④ 步「回读校验」就在同一次编辑器会话里跑，删了它校验会读到不存在的清单。
只删版本目录还顺带保住了 Unity 的 SBP 构建缓存，重建更快。
需要"另存一份"就直接改版本号（如 `1.0.1`）。

**顺带核实**：`TaskPrepare_ESBP`（模拟构建管线）**根本不做输出目录检查**
（只 `CheckBuildParameters()`），所以模拟清单那条路不会被 ErrorCode115 影响，
`Simulate/` 每次覆盖重建，与观察一致。

**反向验证**：临时删掉 `using System.IO;` 跑 `check_usings.py` → 确实 `FAIL` 并点名
`Directory`，确认这一行真被检查覆盖（本工程要求"检查必须能 FAIL"），随后已还原。
7 个静态校验器全 PASS。

**文档**：`Docs/YooAsset_Integration.md` 步骤 3 下新增
《关于 ③ 里的两个构建按钮》，写清"同一版本号第二次必报错"是 YooAsset 行为、
以及「彻底重建」与默认路径的差别。

## 08:55 停用 Gitee，远程只保留 GitHub；并修掉 `git push` 静默挂死

**远程调整**（用户要求"不再使用 gitee"）：`git remote remove origin` + `git remote rename github origin`。

`main` 的 upstream 也就是它。Gitee 仓库本身未删除，只是本地断开。

**★ ★★ `git push` 静默挂死（本次最主要的排查成果）**

现象：首次推送（08:23，`main` 137MB）**成功**；之后的推送全部**零输出卡住** ——
前台被 SIGTERM、后台能挂 6 分钟以上。`ls-remote` 却始终正常。

**排错链（按"最像的先排除"，结果全都不是）**：
1. 文件大小超限？→ 最大 `tips.zip` 36.5MB < 100MB，排除。
2. 网络/代理？→ `git ls-remote github` 秒回，排除。
3. 没有凭据？→ 直接调 `git-credential-manager.exe get` **秒回** `username=Eagle-Lai`；
   `git credential fill` 也秒回。**凭据完全没问题，排除。**
4. 是凭据助手弹 GUI 交互等待？→ 加 `GCM_INTERACTIVE=Never credential.interactive=false` 仍挂，排除。
5. `git -c credential.helper= push` 则**立刻**报 `could not read Username` ——
   说明"挂起"确实发生在**助手被调起之后**，于是把目标锁定到助手内部。

**根因（读 `GIT_TRACE=1` 日志坐实，不是猜）**：日志在收到 GitHub 的
`git-receive-pack-advertisement`（鉴权成功）之后，执行了：

```
run_command: 'git credential-helper-selector store'
  → git config credential.helperselector.selected
  → git config --show-origin credential.helper
  → git config --system -e        ← 就是这里
```

`helper-selector` 想把自己选定的助手写进**系统级** gitconfig，于是调用 `git config --system -e`
**打开交互式编辑器**；非交互环境下就永远等下去。它是 PortableGit 的**系统级**
`credential.helper`（`C:/Program Files/WorkBuddy/.../etc/gitconfig`），所以每个仓库、每次 push 都会踩。

**解法**：
- **绕行（无副作用，随时可用）**：`GIT_CONFIG_SYSTEM=/dev/null git push origin main`
  —— 让 git 忽略系统配置，只剩用户级的 GCM（`http.https://github.com.proxy` 在用户级，不受影响）。
- **根治（已做）**：`git config --system credential.helperselector.selected manager` 写入即可。
  ⚠️ 第一次写报 `could not lock config file ... File exists` —— **不是权限问题，是 08:19 那次挂起
  进程留下的陈旧 `gitconfig.lock`**（该目录其实可写）。`rm -f ...\etc\gitconfig.lock` 后再写即成功。

**教训（可复用）**：git 报 "could not lock ... File exists" 时**先找陈旧 `.lock`，别急着下"需管理员权限"的结论**；
判据是看错误里有没有 "Permission denied"。

**验证**：绕行参数推送成功 `ad727d4af..0ea15d85c`，`local main` == `origin/main` == `0ea15d85c`。

**⚠️ 后续更正（08:59）：上面"根治"那条已证伪。**
系统 gitconfig 确实写入成功了（`[credential "helperselector"] selected = manager` 已在文件里），
但**不带绕行参数的 `git push` 仍然挂死**（`timeout 150` 返回 124）。
⇒ `helper-selector` 是**无条件**去跑 `git config --system -e`，与配置项是否已存在无关，这是它的设计缺陷。
**结论：唯一确认有效的就是绕行参数 `GIT_CONFIG_SYSTEM=/dev/null`，每次推送都带上。**
想彻底解决只能从系统 gitconfig 删掉 `[credential] helper = helper-selector` 一行
（目录可写；但会改动 WorkBuddy 自带 PortableGit 的默认行为，需用户权衡，本次未擅自改）。
另：08:55 那次"第一次写报 File exists"的判断是对的 —— 确实是陈旧 `gitconfig.lock`，不是权限问题。

- 我配的是 **stdio**；stdio 模式下 Unity 插件要在**本机 6400 端口**跑 `StdioBridgeHost` 等服务器来连（`Editor/Helpers/PortManager.cs: DefaultPort = 6400`、`Editor/Services/Transport/Transports/StdioBridgeHost.cs`）。
- 但实测 **6400 未监听**，而 **8080 有一个活的 MCP HTTP 端点**（`serverInfo: mcp-for-unity-server`，由 `python.exe` PID 45064 提供），Unity 正连着它 → **Unity 当前是 HTTP 模式**，它自己拉起了服务端。

**Unity 侧切换位置（读源码得到的确切路径）**：`Window ▸ MCP for Unity` → **Connection** 区 → **Transport** 下拉，选项为 `HTTP Local` / `HTTP Remote` / `Stdio`；旁边还有 `Unity Port` 字段（tooltip 明说"Used for stdio transport"，默认 6400）。窗口里另有 **Transport Mismatch** 警告，正是这种情形的提示。
对应源码：`Editor/Windows/Components/Connection/McpConnectionSection.cs`。

**两条收敛路径**：
- **B（推荐）**：Unity 里把 Transport 切成 **Stdio** → 6400 起来 → 我这边**无需重启 WorkBuddy**，当场可验证。
- **A**：把 mcp.json 改成 `{"unityMCP": {"url": "http://127.0.0.1:8080/mcp"}}` 复用 Unity 自拉的服务端 → 但 **mcp.json 是启动时读的，必须重启 WorkBuddy**，且服务端生命周期绑在 Unity 上。

**判据（以后复用）**：服务端报 `instance_count: 0` + 6400 未监听 + 8080 在听 → 就是 HTTP/stdio 错配，不是插件没装、也不是配置写错。另：包确实装好了，在 `Library/PackageCache/com.coplaydev.unity-mcp@aa5fc638d6`，`package.json` version = **10.3.0**（#v10.3.0 锁定生效）。

**⚠️ 路径更正（12:58）**：`Window ▸ MCP for Unity` 这个**菜单里没有** Transport 选项，它只有四项：`Toggle MCP Window (Ctrl+Shift+M)` / `Local Setup Window` / `Edit EditorPrefs` / `Blender Bridge ▸`。
**Transport 在窗口内**：先 `Window ▸ MCP for Unity ▸ Toggle MCP Window` 打开窗口 → 窗口顶部是 6 个标签 `Connect / Tools / Resources / Generative / Deps / Advanced`（默认停在 **Connect**）→ Connect 页最上面的 **Server** 区块 → 第一行 `Transport:` 下拉（源码 `Editor/Windows/Components/Connection/McpConnectionSection.uxml`，`connection-section` 的 section-title 文案就是 "Server"）。旁边若有 **Transport Mismatch** 警告条即为此错配。切换后如状态显示 Disconnected，点 **Connect**。

**⚠️ 二次更正（13:00）—— 光切下拉不生效，必须点会话按钮。**
用户改完 Transport 后实测：6400 **仍未监听**、8080 仍在听、`instance_count` 仍为 0。
读源码找到原因（`Editor/Windows/Components/Connection/McpConnectionSection.cs:186-240`）：`transportDropdown` 的 `valueChanged` 回调**只做 `MCPServiceLocator.TransportManager.StopAsync(旧模式)`**（且明文注释"Best-effort: stop the deselected transport to avoid leaving duplicated sessions running"），**没有任何 Start 逻辑**。真正启动走 `connectionToggleButton` → `OnConnectionToggleClicked` → `BridgeControlService.StartAsync()` → `TransportManager.StartAsync(Stdio)` → `StdioTransportClient.StartAsync` → `StdioBridgeHost.StartAutoConnect()` → `TcpListener.Start()` 绑 6400。
**按钮文案是"当前模式"的可靠指示器**（`McpConnectionSection.cs:413` / `:433`）：
- stdio 选中 → 运行中显 `End Session`，未运行显 **`Start Session`**
- HTTP 选中 → 运行中显 `Disconnect`，未运行显 **`Connect`**
按钮 tooltip 固定为 "Start or end the MCP session between Unity and the server."；状态文本节点名 `connection-status`，初始 "Disconnected"。
另：8080 那个 `python.exe` 很可能是**孤儿服务端**（源码里多处提到 orphaned server after domain reload），不影响 stdio，不必手动杀。

**给用户的下一步**：看那一行按钮文字 —— 是 `Start Session` 就点它；如果是 `Connect`，说明下拉没生效（需重新触发一次选择，或直接改走 HTTP 方案）。
