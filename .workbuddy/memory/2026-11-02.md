## Unity MCP 支持多个 AI 客户端同时连接（15:40 实测确认）

- 结论：**可以**。同一 8088 端点连续 initialize 出两个独立会话（`Mcp-Session-Id` 6a52cff8… / 4f219d3e…），各自 `notifications/initialized`(202) → `tools/list` 均返回 49 工具；A 在 B 建立后仍正常 list（没被顶掉）；两会话并发 `tools/call read_console` 都成功（A 406ms / B 535ms）。
- 原理：Unity 侧是 WebSocket **客户端**（`WebSocketTransportClient` 单条连 hub），Python 服务用 FastMCP + `StreamableHTTPSessionManager`（mcp 1.30.0：`DEFAULT_MAX_SESSIONS=10000`、空闲 30min 回收）；每个 AI 客户端 initialize 得到独立 MCP session。
- ★红线：**所有客户端指向同一个 URL，禁止各客户端自己用 uvx 拉 server 进程**。Unity 只连一个 hub，且 `PluginRegistry.register` 按 `project_hash` 注册，同工程重复注册会 **evict 旧 session（"superseded"）** → 后起的顶掉先起的，所有客户端一起失联（`transport/plugin_hub.py` `_handle_register` 有日志）。
- 全局共享（会互相影响）：`manage_tools` 的启用/禁用是 Unity 工程级状态（一个客户端关了某组工具，别人也看不到）；场景/资产/Play 模式是同一份工程；`TransportCommandDispatcher` 默认 30s 超时，`refresh_unity wait_for_ready`/打包/ExecuteMenuItem 会串行排队。
- 会话级隔离（互不影响）：`set_active_instance` 存在 `UnityInstanceMiddleware` 的 per-`session_id` state 里（`ctx.session_id` = HTTP 的 `Mcp-Session-Id`），各客户端可各选各的 Unity 实例；客户端重启后 session 丢失需重新 set。
- 传输不能混：Unity 侧 `TransportManager` 的 HTTP Local / stdio 是两套 client，实际只用一套；某客户端只会 stdio 时切过去会让 HTTP 客户端全断。统一 HTTP 最省事。
- 当前实况：Codex `~/.codex/config.toml` 有 `[mcp_servers.unityMCP] url=http://127.0.0.1:8088/mcp`（即已有一个客户端在用）；WorkBuddy `~/.workbuddy/mcp.json` **没有**本工程条目（只有 disabled 的 8082 旧配置）。想双开就在 mcp.json 里加同一个 URL。
