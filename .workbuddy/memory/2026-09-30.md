### 本轮修掉的 11 个真实缺陷（详见 §Z.7.2）

最值得记的三个：

1. **`TryUpgrade` 失败会永久丢塔** —— 原实现"先拆旧塔、后建新塔"，
   新塔资源加载失败时旧塔已归还对象池 → 玩家花了钱，格子上什么都不剩。
   **教训：任何"销毁 + 重建"的流程，只要重建可能失败，就必须先把新的建出来。**
2. **穿透完全无效** —— 原实现在 `_pierce>0` 时把 `_target` 置 null 后 return，
   而命中判定要求 `_target != null`。**分支写了、注释写了"M2 完善"，
   但两条分支的组合条件是自相矛盾的** —— 这类"看起来做了其实没做"最难发现。
3. **AOE 每次命中都 `new List`** —— 与"GC Alloc = 0B"的设计目标直接冲突。

### 环境突破（本轮最有复用价值的部分）

**① 用 MSBuild 做真实编译验证 —— 不再靠"括号配平"猜**

Unity 已经生成了 `Assembly-CSharp-Editor.csproj`，直接调用 VS 的 MSBuild 就能真正编译：

```powershell
& "C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe" `
  Assembly-CSharp-Editor.csproj /t:Build /p:Configuration=Debug /v:minimal /nologo /m
```

它会把 `Assembly-CSharp-firstpass` / `Assembly-CSharp` / `Assembly-CSharp-Editor` 三个程序集全编一遍。
本轮靠它当场抓出 3 个 CS 错误，其中一个是**枚举类型名被同名属性遮蔽**（CS1061），
静态脚本完全看不出来：

```csharp
public EffectType Effect { get { return (EffectType)_t.EffectType; } }  // OK
public int EffectType { get { return _t.EffectType; } }                  // ← 这一行让下面报错
public bool IsLaser { get { return Effect == EffectType.Laser; } }       // EffectType 被解析成 int 属性！
```

**坑**：新增 `.cs` 文件后 Unity 才会把它写进 csproj。未重新生成 csproj 前，
要手工补一行 `<Compile Include="Assets\Scripts\...\X.cs" />` 才能参与编译。
（csproj 被 `.gitignore` 忽略，随便改。）

**② Luban 可以完全脱离 Unity 跑**

`Luban.ClientServer.exe` 是自包含 .NET 程序，设 `DOTNET_ROLL_FORWARD=LatestMajor` 后可直接命令行导出：

```powershell
$env:DOTNET_ROLL_FORWARD='LatestMajor'
& Luban\Tools\Luban.ClientServer\Luban.ClientServer.exe -j cfg -c Luban\.cache.meta -- `
  -d Luban\Config\Defines\__root__.xml --input_data_dir Luban\Config\Datas `
  --output_code_dir Assets\Gen --output_data_dir Assets\ConfigJson `
  --gen_types code_cs_unity_json,data_json -s all
```

于是"改 xlsx → 导出 → 编译 → 跑校验"整条链路都能无人值守跑完，
**不必等人在 Unity 里点菜单**。

**③ 配置表变更一律脚本化**

新增 `.workbuddy/tools/apply_m2_*.py`：每个脚本自带备份、按**列名**（不是列号）定位、幂等。
手改 Excel 踩过的坑本轮就复现了两次：
- 把 `id` 写进了 A 列 —— Luban 的 A 列是 `##` 标记列，**数据必须从 B 列开始**；
- 用写死的列号取 `interval`，实际取到了 `EnemyIndexs`，把一串敌人 id 拿去转 float。

### 数值平衡的发现

`balance_sim.py` 暴露出两个**设计层面**的问题（不是 bug）：

1. **激光塔被严格压制**：性价比 0.700 vs 穿透塔 2.500 —— 没有任何理由建它。
   调 power 后到 1.200（仍低于普通塔，这是有意的：瞬发命中不浪费输出）。
2. **所有塔的 L1→L2 升级都是坏选择**：边际性价比 0.889/0.812/0.167/0.948/0.200，
   全部低于各自 L1 → 玩家的最优解永远是"铺满 L1"，升级形同虚设。
   重排 power 后回到 0.59~1.60。

同时确立了正确的建模口径：**不要算"DPS 比值"**（分母"能同时开火的塔数"无法可靠估算），
而是算**经济余量** + 用几何算出的**可建造格数量**作为塔数上限。
最终结论：所有回合余量 ≥ 1，且第 8 回合建造位用尽后余量转为下降 ——
**这才是后期真正的难度来源，也说明升级在此时才有价值**。
