# 波次回退与本波重试：数据一致性修复

本记录补充并修正同日 `previous-wave/README.md` 的验收结论。此前 90 项检查未覆盖真实塔的战斗相位、负的小数金币余数、重复 HUD 刷新、战斗中出售后重进等场景，不能据此推断重复操作没有问题。

工程为 `D:/FreedomTower_1`，Unity `2022.3.62f3c1`，MCP 插件 `10.3.0`。使用用户当次授权的 stdio / 6400；每次重连按实例与 project/info 核对身份，没有切换工程或猜测端口。

## 修复前证据

`before.jsonl` 为 MCP 在修改前执行 `before-reproduction.cs.txt` 的返回结果：

- 暂停当帧仍返回非零模拟步长，并增加计时。
- 加入 `0.99999` 金后，小数余数成为 `-1.001358e-05`，不满足检查点的合法范围，可能令重试/回退不可用。
- 恢复后开火相位 `0.123 → 0`、索敌相位 `0.037 → 0`。
- 恢复后 HUD 原显示第 1 波，再调用 RefreshAll 变为第 0 波。
- 恢复后的实际战斗时钟为 7.5 秒，内存统计仍为 0；完成下一波时实际战斗计时 15.75 秒，落盘统计仍为 0。

代码核查另外确认：战斗中出售时仅裁掉未完成波的明细，仍保留本波资源、伤害和全局计数，形成无法对应同一波次边界的存档；恢复塔阵时按格位排序还会改变塔的注册/攻击顺序；容量延迟计数修改的是 RunMetrics 的只读副本。

## 最终行为

- `CompletedRoundCount` 表示已完成波数和下一波零基游标；`CurrentRoundIndex` 统一表示正在打或准备打的正式波号。HUD、完整刷新、波次完成事件和编辑器验证工具同步使用该口径。
- 波次完成后先更新游标、账目、资源元数据、计时和状态，再发布 RoundClearEvent，避免监听方观察到一半旧、一半新的状态。
- 内存检查点保存塔的开火/索敌/后坐/光环计时、炮管姿态和原注册顺序。恢复时同步恢复这些状态，继续使用原有塔的类型、等级、格位和投入。
- 暂停/继续切换当帧清零模拟步长，防止消费旧 delta 或重复累计计时；恢复时钟时也清掉旧步长。
- 小数金币余数保持在 `[0, 1)`，随同一局的资源存档恢复；旧记录未带此字段时缺省为 0。存档格式版本及 SQLite schema 未升级。
- 每次开波保存完整开波边界。战斗中卖塔时保存该完整边界，重试或重进时本波交易、收益、伤害和统计一起撤销；准备阶段卖塔仍立即保存当前完整局面。不会保留卖塔返还又复活同一座塔。
- 保存与读取运行统计时同步实际计时、生命元数据；波次游标、逐波 ordinal、出生/击杀/漏怪和全局总数必须一致。游标 0 是合法的第一波准备记录。
- 不一致的旧局内进度整份拒绝接管，不把它的资源接到第一波；不猜测修补已经丢失的历史。读取拒绝本身不删除源记录。合法旧阵型和通关后重玩入口保留。
- 容量延迟通过流程层更新真正持有的统计，不再修改克隆副本。

回退历史依旧只属于当前对局；退出、切关或重开后不伪造更早的检查点。准备阶段连续回退的最低边界为第一波开打前。
