## 一、工作前提与实施方式

遵守工程 AGENTS.md，先读取 `ProjectSettings/ProjectVersion.txt`，核对 Unity 版本和 unityMCP 目标实例。当前工程为 Unity 2022.3.62f3c1，使用 `unityMCP`、HTTP Local 8082，实际信息以现场核对为准，不使用另一个工程的 MCP 验证结果。

先读取相关代码、Git 历史及项目内 `.workbuddy/memory` 的相关记录。历史记录和代码注释需与当前实现交叉核对，不能将旧注释当成现状。先简要报告审计发现和实施方案，然后直接实施。一般实现细节自行判断；遇到真正影响产品行为或无法兼容的重大取舍时，给出具体方案和原因。

保留已有未提交改动，尤其不要覆盖 Configs 和 Launcher 中已有的配置失败重试修复。不擅自回滚用户改动，不修改无关工程。

## 二、目标启动顺序

APK 正常启动必须严格遵循：

`Boot 场景显示 HotUpdateView → 准备本地启动基线、选择服务器并检查更新 → 下载、校验并加载热更 DLL → 初始化 YooAsset → 检查、下载并校验完整 AB 资源及依赖 → 确认 DLL 与资源版本兼容、启动资源完整 → 从 YooAsset 加载 Main 场景 → 显示 LoadingView，完成配置与游戏初始化 → 显示 SplashView → Splash 结束后进入主菜单。`

LoadingView 在 SplashView 之前，这是本次明确要求，不沿用目前 Splash → Loading 的顺序。

HotUpdateView 必须在 DLL 热更开始前即可正常显示，并贯穿 DLL 和 AB 更新全过程，不能在中途切换为另一套默认更新界面。进入 Main 之前不能提前实例化游戏业务对象或执行依赖配置的游戏流程。

## 四、HotUpdateView 的架构要求

优先把 HotUpdateView 的启动用实例直接配置到 Boot 场景，使其成为 APK 启动首屏。

当前 HotUpdateView 脚本位于 FTProject.Runtime 热更程序集，不能简单把现有预制体原样挂进 Boot 后就认为可用。必须解决 DLL 尚未加载时的脚本和序列化依赖：

1. Boot 首屏所需的控制器、协议与必要依赖必须在 AOT 阶段可用。
2. AOT 层不能直接引用尚未加载的热更类型。
3. 必要时拆分 AOT 启动视图与热更侧更新协调器，以小接口传递状态；保留现有视觉设计及有意义的交互能力。
4. 启动首屏不能依赖待下载的 AB、热更脚本、字体或多语言表。
5. 字体、材质、Shader、图片、按钮事件和本地化组件也必须检查依赖，不能仅迁移根脚本。
6. 避免重复创建 Canvas、EventSystem、更新界面或 DontDestroyOnLoad 对象。

HotUpdateView 可以作为随 APK 发布的稳定启动外壳，不强求其场景结构本身能够热更。明确说明哪些内容可热更、哪些需重发 APK。

可以在稳定外壳上接入缓存或更新后的文案、字体、图片等可更新内容，但不能形成“下载更新界面之前必须先显示更新界面”的循环依赖，也不能破坏失败恢复。

## 五、统一 DLL 与 AB 更新展示

将现在分散在 BootLoader、BootHotUpdateGate 和 Launcher 中的更新展示整合到 HotUpdateView。

至少显示：

- 当前阶段与具体状态。
- DLL 下载和校验进度。
- AB 下载文件数、字节进度、速度。
- 无更新、完成、失败、重试和离线状态。

总体进度不能在 DLL 完成后就显示 100%，AB 仍在下载却显示“准备就绪”。阶段进度与总体进度分开表达，尚无总量时显示不确定状态。

暂停、继续、重试按钮应有明确的适用阶段；不支持暂停的阶段应禁用或隐藏相关操作。防止重复点击、重复下载、重入、回调重复及销毁后回调。

整理或替换原 BootHotUpdateUI 的正常启动用途，避免两套更新页面并存。Main 中不再无条件重复执行一轮 DLL/AB 更新；保留必要的受控恢复路径。

## 六、保留 YooAsset 与更新完整性

继续使用现有 YooAsset 和 HybridCLR，不另建一套平行资源系统。沿用工程实际安装版本的 API，不能照搬旧版本示例。

保留并检查：

- 服务器发现、手工覆盖、超时及可达性检测。
- 首包 StreamingAssets 基线与 persistentDataPath 缓存。
- 有效缓存复用、差异下载、断点恢复和完整性校验。
- Host/Offline 模式和编辑器模拟模式。
- 相同版本号下缺失资源的补齐。
- 场景、字体及其他依赖包的完整性。
- 已下载版本不被旧包内基线错误覆盖。

重点解决 DLL 与 AB 发布或更新不一致：

- 不允许部分 DLL 更新失败后随意混用不兼容版本继续启动。
- 检查现有版本清单、发布顺序和激活机制是否足够。
- 必要时增加兼容性标识、暂存与提交机制。
- 已加载的热更程序集不能在同一进程中随意卸载或替换，恢复方案必须尊重此限制。
- 区分 DLL 下载重试、程序集加载失败、AB 初始化失败、下载失败及配置失败。

断网或服务器不可达时，只有本地存在完整且兼容的 DLL/AB 组合才允许离线进入游戏。否则停留在可理解、可恢复的 HotUpdateView，不能黑屏、无限静默等待或带残缺资源进入 Main。

梳理外层场景加载超时与内层更新重试的关系，避免下载仍正常进行时，被原 BootLoader 的固定 60 秒等待误判为加载失败。

## 七、LoadingView 与 SplashView 必须尽可能完整支持热更

这两个界面在 DLL/AB 更新完成后才加载，应通过 ResTable/YooAsset 使用当前激活版本的预制体及依赖，其布局、图片、字体、文案和热更脚本行为都应能够更新。

检查 Resources 兜底是否会掩盖 AB 加载错误或误用 APK 旧副本。真机正常路径不得静默回退到挂有热更脚本的旧 Resources 预制体。

如调整资源目录，必须保留 `.meta`/GUID，并同步引用、ResTable、收集器、生成器和构建校验；不要只移动文件导致资源失联。

Main 内的初始化顺序需要重构：

- LoadingView 负责实际配置和游戏初始化进度。
- 初始化成功后关闭 LoadingView，再显示 SplashView。
- Splash 完成后才允许进入主菜单或开始游戏。
- 配置加载失败保留有界重试、明确错误及恢复能力。
- ConfigLoadedEvent 等事件不能提前触发游戏流程，需梳理全部订阅者。
- 加载和过场期间不得提前建关、播放战斗或暴露未初始化界面。

## 八、多语言必须纳入完整热更设计

保留当前语言选择、存档和运行时切换功能，不能只保证英文或中文硬编码可见。

当前 LanguageManager 位于热更层，LocalizationSettings 从 Resources 读取，多语言表在 Configs 加载后才可用。必须解决两个阶段的依赖。

### A. DLL 加载前的 Boot 阶段

- 使用 AOT 可访问的最小本地化基线。
- 尽可能读取玩家已有语言选择，并保持与现有存档格式兼容。
- 没有存档、缓存损坏或缺少字体时有可靠回退。
- 文案覆盖 DLL/AB 下载、错误、重试、离线及按钮状态。
- 不为显示更新文案而提前依赖尚未下载的资源。

### B. 热更资源就绪后的阶段

- 从当前激活的资源加载最新多语言表、默认语言配置、支持语言列表、字体和本地化图片。
- 及时刷新词典、字体映射与已显示内容，避免静态缓存一直持有旧配置。
- LoadingView 和 SplashView 首次显示时就应尽可能使用最新本地化内容，不能等它们关闭后才初始化语言。
- 保留玩家主动选择的语言，更新默认配置不能覆盖玩家选择。
- 保留 TextLocalizer、ImageLocalizer 和语言切换事件的完整行为。
- 缺 key、空翻译、格式占位符错误、缺字体均需可回退且不崩溃。

如需要让 Boot 使用上次成功更新后的本地化缓存，应明确缓存格式、版本、校验和回退策略，不能让损坏缓存阻断首屏。

明确“现有语言的文案、字体、图片和默认配置更新”与“新增语言涉及 AOT 类型或枚举变化”的支持边界；不能声称所有 AOT 结构都可热更。

## 九、尊重历史故障与发布约束

已知必须防止回归：

- Boot 从 Build Settings 丢失、APK 直接进入 Main，导致热更脚本 missing 和黑屏。
- 新清单已激活但 bundle 未下载完成，下一次启动界面残缺。
- 新 DLL 配旧配置包导致缺表。
- 配置加载失败仍被 IsLoaded 缓存为成功，后续无法重试。
- 只构建新 AB、未部署，服务器 FreeTower.version 仍指向旧版本。
- IL2CPP 裁剪导致字体/UI API 在真机 MissingMethodException。

保持 Boot 为 APK 启动场景，Main 继续从 AB 加载。必要的 AOT 变更需重发 APK，必须明确说明旧 APK 能否兼容新资源，不能把需要新 APK 的改动当作仅发 DLL 即可。

同步维护构建发布流程、资源收集、部署校验及过时注释，避免生成器再次生成旧架构。发布验证需检查实际服务返回的版本、清单、DLL 校验清单和 bundle，而非仅查看本地构建目录。

采用必要且有意义的自动化检查和运行取证。未实测的项目明确列出，不用静态检查代替 APK 验证。
