## 四、必须按真实机制设计

### 1. 塔体系与购买成本

塔数据位于全局 `Luban/Config/Datas/TowerInfo.xlsx`，不存在逐关塔表。当前只有普通、火力、减速三类，各三级：

| 类型 | 一级建造价、两次升级增量价 | 满级累计投入 | 实际职责 |
|---|---|---:|---|
| 普通塔 | 32 / 90 / 180 | 302 | 地空单体即时伤害，射程内优先对空 |
| 火力塔 | 44 / 110 / 210 | 364 | 地面即时范围伤害，不能对空 |
| 减速塔 | 30 / 85 / 170 | 285 | 地空减速光环，直接伤害为 0 |

100 开局金可以买三座普通塔，或两座普通塔加一座减速塔；普通、火力、减速各一座需要 106，不能假设开局即可三种齐备。

升级按 `upgradeTo` 链和增量 `prices` 扣费。出售收入按当前等级 `sellPrice × Global.sellRefundRate` 及代码取整计算，不能自拟返还比例。减速取最强效果，不叠乘；当前三级减速分别为 16%、24%、32%。火力塔 AOE 半径来自 `BulletData`，不能把每次范围伤害固定算成命中全波。

默认冻结全局 `TowerInfo.xlsx`、`BulletData.xlsx`、`Global.xlsx`，以保留第一关基准。所谓为后续关卡设计“防御塔体系”，是安排三类塔的职责、数量、布局、升级与资金时机。若实际证据表明必须改变全局塔参数，应单独列出影响第一关的具体问题与方案，不能悄悄修改共享表或新增逐关倍率。

### 2. 怪物、路线与波次

- 护甲按 `damage × (1 − Clamp01(armor))` 减伤；`hp/(1−armor)` 只能作为分析指标，不能替代击杀取整、过量伤害、有效射程时间和实战结果。
- 飞行怪直达终点，不走地面绕路。必须单独计算对空压力；普通塔优先打空中时还会减少地面输出。
- `reward<=0` 会使用默认击杀奖励，不能填 0 来制造零收益怪；漏怪伤害也有默认值回退。以实际生效值核算。
- 漏怪数与扣血数不同，重型或关键怪可能一次扣多点生命。
- 自由布塔改变地面最短路径，完全堵死路线的建造会被拒绝。当前允许在怪物脚下合法建塔，落地后地面怪改道；预览路径本身不改变实战路径。
- 将路线延长、同一敌人离开后再次进入塔射程、空地火力分配纳入策略。不要把塔数、满铺率或路线长度当作评分条件，也不要依赖无限出售重建拖延才能通关。
- 当前每个 Round 对应一个 EnemyList；全部计划敌人成功出生并完成击杀或漏怪结算后，才发清波奖励。
- `RoundData.interval`、`EnemyList.interval`、`enemyInterval` 分别影响出生时间轴，单位为毫秒。
- 当前实际自动开下一波等待读取 `Global.autoNextRoundDelayMs=2500`；不能仅修改 `SceneInfo.waveIntervalMs` 就声称改变了真实节奏。
- 当前 `maxEnemyAlive=200`、`enemyPoolSize=256`。单波总数不等于同屏数量；达到同屏上限会暂缓出生，应记录实际峰值与暂缓，不靠扩大容量掩盖问题。
- 不虚构英雄、技能、利息、工资、额外伤害类型或代码未实现的敌人能力。

## 七、经济紧凑性的量化口径

逐波、必要时逐操作记录现金流，所有关卡从 100 开始：

`当前余额 = 100 + 已实际击杀收入 + 已到账清波奖励 + 已出售返款 − 已支付建造费用 − 已支付升级费用`。

任何操作前缀都不得出现负余额；不能提前消费未击杀怪物的奖励，也不能用本波完成奖励支付本波开战前的防守。存在漏怪时，不能仍把该怪当作击杀收入计算。

以一座当前有战术价值的塔或下一次必要升级的价格作为资金单位，逐关提出具体目标区间：关键波前余额、首次升级时间、重大投资等待时间、末波开打前可用资金。说明目标为何符合该关地图与压力，而不是给全关统一乘数。

重点检查：

- 开局既有合法生存解，又不能覆盖全部威胁。
- 收入能在下一次必要投资之前到账，但不能让玩家在多数波次毫无取舍地同时满足全部建造与升级需求。
- 击杀收入、清波奖励与出怪顺序相互配合，不形成“必须先购买才能击杀、必须先击杀才能买得起”的死锁。
- 末波结束后的现金单独记录；最后一批击杀金与末波奖励可能已无法用于战斗，不能仅凭结算余额判断经济过松。
- 短路线、盲目铺普通塔、无对空安排、忽略减速、错误升级顺序等对照策略应出现可解释的效率损失或漏怪；不得预先伪造其必败结论。

设计阶段给出的预算与理论收益必须标记为预测，实际结果由对应版本的回放校验。发现预测与实战不符时，修正模型或手工调整相关表项，不自动降低整关难度来迎合某个代理。

## 九、评分、导出和全局摘要闭环

`LevelRatingEvaluator` 是唯一评分入口。五星要求满血、零漏怪、击杀全部计划敌人且战斗时间不超过 `parCombatTimeMs`。评级使用模拟战斗时间，不使用墙钟耗时，也不能靠切换 1×/2×/3× 绕过。

逐关手工核对 `expectedWaveCount`、`expectedEnemyCount`、`difficultyTier`、Boss 集合、critical 集合和评级门槛。实际 `type==5` 的 Boss 集合必须与配置吻合，关键集合必须有效并包含 Boss。出生数、击杀数、漏怪数以及逐波汇总必须守恒。

战斗数值变更后，旧 Par、旧操作证据与旧校准状态不再自动有效。按真实参考回放校准时间，明确版本、操作记录和合理余量；不得单纯放宽 Par 来掩盖无法守住或错误计时。`balanceRevision`、`ratingRevision`、`planHash` 等按现有语义更新并记录来源，不复用旧内容身份声称重新认证。

手工源表与导出链严格执行：

1. 手工完成本批玩法数据和当前所需评级字段；检查引用、数量、类型和所有关卡初始金币等于 100。
2. 在编辑器空闲时使用 `Tools/塔防/3. 导出配置表（Luban）`，对应 `FTProject.EditorTools.LubanExporter.ExportFromMenu()`。先核对当前入口实现及程序集保护逻辑，不直接运行带交互暂停的旧批处理。
3. 按 `Configs.CalculateRuntimeContentHash` 的实际算法只读计算摘要：固定顺序的八张完整 JSON 原文，去 BOM、统一 LF，再加按 ID 排序的全部评级关键字段。不能用重新序列化后的近似内容代替生产算法输入。
4. **手工将新摘要填入 L01—L30 全部 30 行 `LevelRating.runtimeContentHash`。** 它是全战役共享封印，并非每关独立摘要；L01 只允许因此修改该字段。
5. 再运行一次正规 Luban 导出。只读复算应一致，并核对源表与导出字段吻合。不能调用脚本批量写评级表，也不能直接改 JSON 完成封印。
6. 在加载正式配置的新局中确认 `[Rating] Runtime configuration SHA256 verified`，记录实际加载摘要；随后运行本批回放。
7. 如果回放后又手工修改了战斗数据、Par 或参与摘要的评级元数据，重复导出、只读计算、手工回填、再次导出及必要回放，最终报告只引用最终版本。

`runtimeContentHash` 自身不参与摘要，所以以上流程没有自引用循环。L01 的基准数据与其他评级字段保持不变；若发现它存在独立历史校准问题，报告该问题，不擅自扩大修改范围。
