# 提交与工作记录规范

> 本规范约束"工作记录 / 记忆文件"与"git 提交"的**先后顺序**与**范围**。
> 2026-10-16 立项、当日生效（起因见 §2 反例）。

## 1. 铁律：先写记录，再提交

**每一次 git 提交之前**，必须先把本次工作的记录写完：

1. **当天工作日志**（`.workbuddy/memory/YYYY-MM-DD.md`）——追加本次工作的完整小结
   （做了什么、验证结果、遗留事项）；
2. **长期记忆**（`.workbuddy/memory/MEMORY.md`）——若本次产生了"跨会话必须遵守的
   不变量 / 约定 / 踩坑"，同步更新对应条目；
3. **然后再执行** `git add -A` → `git commit`（→ 需要时 `git push`）。

记录与代码必须落在**同一笔提交**里。

> **终态信息例外**：提交结果（commit sha、push 结果）**以 `git log` / `git ls-remote`
> 本身为准**，不要求写进当笔记录 —— 避免"写 sha → 产生新残留 → 再补提交"的死循环。
> 如确需在记录里提及，留到**下一笔提交前**随其他改动一起写入。

## 2. 反例（为什么立这条规矩）

2026-10-16 的工作中出现过两次"**先提交、后写记录**"：

- 记忆文件的更新落在提交之外 → 工作区出现新残留 → 被迫发起"补提交"；
- 记录与对应代码不在同一笔提交里，追溯时错位。

## 3. 提交范围：一律全部一起提交

（沿用 2026-10-16 约定）

- **每次一笔**：不拆、不挑——含全部改动（未跟踪 / 缓存 / 产物）；
  `Bundles/`、`Builds/`（.apk）、`HotUpdateServer/` 等按既有 git 忽略规则除外；
- 提交信息写清"做了什么 + 验证结果 + 遗留"，中文、可追溯。

## 4. Checklist（提交前逐项过）

- [ ] 当天工作日志已追加（含验证结果与遗留）
- [ ] 长期记忆已按需更新（新不变量 / 约定 / 踩坑）
- [ ] 记录里**没有**"之后还要补写"的尾巴（终态信息留给 git 本身）
- [ ] `git status` 检查：本次意图内文件齐全、无误伤文件
- [ ] `git add -A` + `git commit`（一笔）
- [ ] 需要同步时 `git push`，并用 `git ls-remote` 核对 sha
- [ ] **提交后不再写盘**；若不得不写 → 并入下一笔提交（不得静默遗留）
