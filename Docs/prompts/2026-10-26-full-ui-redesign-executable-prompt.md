# 《自由人塔防》全界面深色科技 UI 重设计执行 Prompt

## 角色与任务

你是一名资深手游 UI/UX 设计师、游戏界面视觉设计师与交互设计负责人。请为《自由人塔防》重新设计完整的游戏 UI 体验。你的工作范围是界面视觉、版式、信息层级、交互呈现和设计交付物；不要编写、修改或评审程序代码，不要改动 Unity 场景、Prefab、配置表、资源登记、热更包或工程设置，也不要把实现架构当作设计结论。

本任务不是给现有画面换一套配色或润色按钮，而是以原有主题“深色科技面板”为设计锚点，对全游戏的页面结构、视觉层级、控件关系、状态反馈和品牌表现进行系统重构。最终界面需要有鲜明的新设计面貌，同时让玩家一眼认出这是同一款游戏。

请独立作出设计判断并完成全部产出，不要只给原则、提案或少量首页示例。不要在开工前向用户追问；遇到非关键缺失信息时，根据本 Prompt 的明确约束和项目现有设计证据作出审慎假设，并在交付说明中标注假设。

## 项目背景与不可变规则

- 游戏：单机 2D 塔防，项目名称《自由人塔防》，Android 目标，横屏 16:9；主设计基准为 1920×1080。保持既有横屏产品形态，兼顾 1280×720、1024×768、2340×1080、2560×1080 与设备安全区。不要因为 Android 手机而擅自改为竖屏。
- 核心循环：选关 → 查看关卡信息 → 备战与建塔 → 迎战多波敌人 → 获得评级 → 下一关、重玩或返回选关。
- 关卡、波次和评级容量由当前有效配置决定；画面中实际显示的关卡、波数、金币、生命、塔属性、敌人数、用时和评级应来自当前游戏状态。不要照抄截图中的历史测试数字，不要虚构货币、商城、抽卡、联网账号或剧情系统。
- 三种炮塔的定位为：Normal 单体快速攻击，Power 范围攻击，Retard 减速控制。保留其定位、相对信息关系和玩法规则；可重新设计视觉图例、标签、状态和比较方式。
- 工程为无声版本：不要在界面中添加音量、音乐或音效选项。可设计与规则相符的视觉反馈和可选触觉反馈提示。
- 保留当前游戏玩法、评级、经济、存档和操作结果的含义。可以重新表达界面流程和呈现交互，但不能创造会改变战斗规则的玩法。金额、评级条件、解锁规则和塔数据统一使用动态数据，不在设计稿中固定写入测试数值。
- 设计语言仍以深色科技面板为核心，延续现有青色交互强调、金色奖励、红色危险提示与机械切角的识别资产；但不要机械复刻现有大面积同色面板、发光描边和重复按钮。
- 当前工程截图与相关本地设计记录仅作为了解游戏信息与操作的参考。它们不是最终设计模板，不得把线框或旧截图重新贴皮后作为完整重设计。

## 设计目标

1. **延续而非丢弃主题。** 深色界面仍应有战术终端、精密机械与能量显示的气质；通过真实的塔防场景、炮塔、路线、敌人剪影和材质语言连接品牌与玩法。让主菜单、战斗、图鉴与结算看起来属于同一个游戏世界。
2. **形成清晰的新构图。** 不再让每个页面都成为同一个居中面板、标题、按钮列表的变体。根据页面任务选择战场全屏叠层、左右分栏、卡片浏览、紧凑操作条或窄幅确认框。
3. **先服务玩家判断。** 在选关、战前、战斗和结算里，让玩家先看到当前最重要的信息与下一步动作；把长说明、评级细则和次要统计放到恰当的次级层级。
4. **把科技感用于传达状态。** 网格、刻度、扫描线、能量边缘、信号指示与动效只有在表达地图、进度、选中、危险或确认时才使用。控制装饰密度，不使用无意义的随机数字、伪代码、密集网格、全屏光晕或重复发光框。
5. **保证语言与设备适配。** 完整考虑简体中文、繁体中文和英文。长短语言切换后保持布局平衡；支持安全区和比例变化；触控目标在真实手机尺寸下易点按。
6. **建立可学习的统一交互。** 同类按钮、返回、关闭、确认、禁用、选中与页面标题在全游戏拥有一致的含义、位置规律和视觉状态。玩家不需要猜控件怎么用。

## 视觉系统要求

先提出并应用一套有明确名称和用途的设计令牌，令牌用于令设计稳定，不代表实现代码。颜色必须兼顾区分和对比度，不要把所有信息压到青蓝一色。

|---|---|---|
| 深空底色 | `#080B12` | 开屏、页面背景和外层空间 |
| 战场底色 | `#111722` | 棋盘和游戏场景衬底 |
| 主面板 | `#1E2939` | 主要交互区域 |
| 次级面板 | `#252F40` | 卡片、工具区和信息分组 |
| 高能青 | `#35E0FF` | 聚焦、选中、主交互和进度 |
| 战术金 | `#FFC94D` | 金币、星级、奖励与最佳纪录 |
| 警戒红 | `#FF4D5E` | 生命危险、失败和破坏性操作 |
| 过热橙 | `#FF7A29` | 火力塔、警示与待确认状态 |
| 冷凝冰 | `#7DE8FF` | 减速塔和冷态能力 |
| 主文本 | `#E8F0FA` | 页面标题、关键数据和主要操作 |

### 字体、组件与图形

- UI 正文、按钮文字和数值采用清晰、易读、涵盖中英文字形的无衬线字形；品牌展示标题可使用有特色的显示字，但不得让显示字体扩散到小字号数值、错误信息和长说明。
- 数字采用便于比较的等宽宽度或表格数字效果；单位紧邻数值，标签与数值在各页面保持一致。
- 建立清晰的字号等级：品牌展示标题、页面标题、分区标题、主要数据、按钮与正文、次要说明。按照实际 Android 设备观看距离核对屏幕文字，不以 1920×1080 文件中“看得见”作为唯一标准。
- 统一塔型图标、怪物头像、资源符号、星级、返回/关闭符号与状态徽标的轮廓、描边粗细、视觉尺度和光照方向。重复使用的符号在首次或歧义场景下配上文本标签。
- 面板边缘使用精密机械结构的克制表达。重要主操作与普通信息卡需有清楚区别；不在每个元素周围都添加同等亮度的框线。
- 建立动效节奏：操作反馈应迅速、可预测；胜利、解锁和加载阶段可有少量有目的的表现。避免无操作时持续闪烁、抖动、扫描或占据注意力的背景动画。
- 不要在应用 UI 上加入文档式说明、设计者批注、红线尺寸、开发者注释、Lorem Ipsum 或假数据。

## 交互与信息架构要求

- 点击、滑动、拖拽、长按和返回操作应有一致的视觉提示与反馈。主要动作优先采用直接、易发现的点按；长按不得成为玩家唯一能发现的关键操作。
- 塔防建造展示至少两条易理解的操作路径：选中塔型后点按合法地块，以及拖动塔型到地块。拖动是快捷方式；若现有限制使双路径无法使用，保留原操作规则并通过醒目的引导呈现，不得虚构不可用功能。
- 选中塔时显示塔身份、等级、主要属性、关键升级变化、价格和可用操作；射程或影响范围应与地图位置关联且可关闭。出售需要清楚告知对象、返还金额和操作后果，并提供取消机会。
- 把“继续、开始、下一波、重开、返回选关”分别表达清楚。若某项在特定状态下不可用，直接说明原因；没有后续关卡时展示完成状态与仍有效的去向，不把不可操作的状态伪装成按钮。
- 设置中的语言选择需要明确展示当前选择；“重置存档”采用高风险警示与二次确认，明确将清除的进度，普通设置项不得借用危险色。
- 将提示放在原因发生的位置附近。金币不足靠近建造价格；地块无效靠近当前落点；保存失败明确说明成绩尚未保存并提供清晰重试或离开路径。
- 屏幕上的重点信息用数值、形状、标签、动态反馈等组合表达；关键内容不单靠颜色。支持较大文字阅读与清晰对比。所有图标按钮应容易点按且不会相互挤压。

## 必须覆盖的界面与状态

交付完整的页面与状态清单，逐项设计以下范围。若游戏当前不存在的页面在项目文档中明确列为计划界面，仍需提供设计稿，并标注“规划界面”；不要冒充它已在当前运行版本实装。

### 启动与等待流程

1. **SplashView 开屏：** 品牌标识、中文/英文品牌名、克制的启动状态；成为后续游戏 UI 的视觉入口。
2. **LoadingView 加载：** 当前阶段、可信的进度呈现、短小且有用的玩法提示、失败状态。不要让百分比、阶段文字和动画彼此矛盾。
3. **HotUpdateView 热更新：** 检查、下载、校验、完成、暂停、继续、重试、失败等需要呈现的阶段；显示玩家理解所需的进度和原因，不暴露开发实现字段。

### 主流程与战斗

4. **MainMenuView 主菜单：** 新设计主视觉；继续进度/开始游戏；图鉴、设置与退出等当前已有入口；展示总进度但不要让统计抢过主操作。
5. **SelectView 关卡选择：** 全量关卡导航、已通关星级、已解锁/未解锁/当前进度状态、快速浏览方式和返回入口。不能只交付第一关卡片。
6. **SelectLevelItem 关卡条目：** 普通、当前选中、已完成、未解锁、可继续、已有历史星级和新记录等必要视觉状态。
7. **LevelDetailView 战前简报：** 关卡身份、地图预览、波数、初始金币与生命、敌人组成/威胁特征、最佳成绩与五星条件、继续/挑战/重开/返回。优先服务战术决策，避免把所有内容堆成一段居中文字。
8. **GameIntroView 玩法说明：** 用图示化短步骤解释炮塔建造、路线规则、波次和胜利条件；提供符合上下文的返回/关闭入口。
9. **HudView 备战状态：** 金币、基地生命、波次、塔型/价格、开始波次、倍速/暂停等。清楚呈现现在可以做什么，以及下一步是什么。
10. **HudView 战斗中：** 维持棋盘主体可读；资源、当前波次、塔栏、倍速与暂停等位置稳定；敌人、路径、生命和伤害表现不得互相淹没。
11. **HudView 建造状态：** 塔型选中、拖动、合法落点、非法落点、金币不足、建造成功与取消。展示落点预览并保留对棋盘的观察空间。
12. **HudView 选中塔状态：** 当前塔高亮、攻击范围、状态信息、可升级、金币不足、满级等反馈；面板和棋盘选中目标之间保持明确关联。
13. **TowerInfoView 塔操作面板：** 正常塔/火力塔/减速塔、各等级、可升级/资金不足/满级及出售入口。展示对玩家有决策价值的属性和升级前后差异，减少难懂缩写。
14. **PauseView 暂停菜单：** 明确暂停状态；继续为当前首要操作；重开、设置和返回选关按风险分组，文案说明离开或重开对当前进度的影响。
15. **TipsView 与情境提示：** 短暂反馈、警告、操作成功、操作失败、金币不足、路径限制等。设计出现、停留和退出的视觉优先级；避免长期遮挡关键 UI。

### 图鉴、确认和结算

16. **TowerCodexView / TowerCodexItem 塔图鉴：** 三种塔型的视觉展示、用途、攻击特点、优势/局限、关键属性比较；聚焦当前塔型，允许轻松前后切换。
17. **MonsterCodexView 怪物图鉴：** 若未实装则按规划界面交付；可浏览怪物形象、类型、威胁标签和有价值的战术提示。不发明未被项目资料支持的敌人属性或故事。
18. **SellConfirmView 出售确认：** 塔型与等级、返还金额、不可逆后果、确认与取消。警示视觉明确但不过度压迫。
19. **ConfirmView 通用确认：** 至少展示重置存档案例和普通离开/重开案例。标题必须描述具体动作；正文解释后果；按钮使用明确动词，不依赖“OK/确认”猜测。
20. **LevelClearView 胜利结算：** 关卡胜利、实际评级、本次与历史最佳、新纪录、剩余生命/漏怪/击杀、战斗时间、关键评级原因、下一关/重玩/返回。用荣誉表达强化成就，不重复堆叠相同星级信息。
21. **LevelClearView 失败结算：** 清楚说明失败；突出最关键原因、进度和建议的下一步；重试/返回应易辨识。失败状态不可仅通过颜色变化表达。
22. **LevelClearView 保存中/保存失败：** 仅在对应状态出现；阻止把尚未保存的成绩误呈现为已落盘的新纪录；明确重试和退出路径。
23. **末关完成状态：** 正确呈现“没有下一关”，给出有效的重玩或返回去向，不把“已是最后一关”当作主要操作按钮。
24. **跨界面通用状态：** 加载、空内容、锁定、选中、禁用、不可建造、无足够金币、断网/热更失败（如该状态适用）、确认中、保存失败等。空状态与错误状态需告诉玩家发生了什么以及可执行的下一步。

## 响应式与可读性要求

- 以 1920×1080 横屏构图建立整套页面，再检查 1280×720、1024×768、2340×1080、2560×1080 与带安全区设备。重点不是把元素等比缩小，而是保证主信息、操作和返回路径始终完整、可读、可点击。
- 战场中心必须在各适配视口内保持足够空间；HUD 与弹窗不得挡住路线入口、基地、主要敌群或当前选中塔。必须交付至少一张 1024×768 与一张 2340×1080 的代表页面适配稿。
- 语言切换要分别检查简体中文、繁体中文、英文的标题长度、按钮长度、数字单位、换行与左右留白。英文长词不可挤出按钮或被压成过小字号。
- 对关键文本、图标、描边和背景检查实际对比度；主要文字与交互元素不能依赖暗钢色细线来表达。关注低亮度屏幕、眩光和色觉差异场景。
- 重要按钮触控区域应适合手持设备；相邻按钮之间有足够间距，避免把误触风险交给玩家。
- 所有弹窗都有明确退出/取消路径。开启弹窗时背景层次可辨识，但背景不应与弹窗争抢注意力。

## 最终验收标准

- 交付覆盖完整页面与重要状态，而非局部换肤或首页概念图。

- 玩家能够迅速找到当前目标、重要数值和首要操作；主次按钮和返回路径没有歧义。
- 选关、战前、战斗建造、炮塔操作、出售确认、设置重置、结算及保存失败等完整操作链都有相应画面。
- 低星失败、游戏终局、热更新失败与成绩未保存等状态能清楚解释原因和下一步动作。
- 简繁中文及英文可以在真实文案长度下呈现，不挤压控件、不遮挡信息、不退化成统一缩小字体。
- 战斗 HUD、棋盘和选中塔在不同画面比例下仍可辨识，重要控件不被安全区或弹窗遮挡。
- 所有图标和颜色在反复出现时语义稳定；重要信息不只依赖颜色。
- 不虚构游戏规则、数值、功能、敌人特性或未保存的成绩；不把开发文档术语带入玩家 UI。
- 交付中包含本 Prompt 要求的草图、导航图、设计系统、逐页稿、状态稿、适配稿、交互规格和验收结果。
