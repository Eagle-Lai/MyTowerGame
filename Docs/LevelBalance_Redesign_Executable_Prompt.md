## 任务

请在 `E:/MyTowerGame` 中，基于现有实现，直接完成一轮关卡、怪物、防御塔、经济、刷怪节奏和 **1—5 星通关评分**的重设计和落地。目标是接近《坚守阵地》（Fieldrunners）的体验：开局规划路线，战斗中用击杀收益补塔和升级，以普通塔、范围火力和减速配合处理逐渐增强的敌群；每隔数波出现需要调整布防的压力点。

## 二、关卡结构和节奏

保留现有 **20 个关卡 ID**，每关配置 **20 个独立 Round，每个 Round 仅包含 1 个 EnemyList**，形成 400 个可独立清场、发奖和布防的波次。不要把 5 个 Round 各塞 4 个时间轴编组后，就当作已经满足 20 个完整波次。

玩家界面统一使用“第 w/20 波”。实际序号来自本关 Round 游标，不使用每个 Round 都从头计数的编组索引。

单关节奏：

| 波段 | 目的 |
|---|---|
| 1—4 | 小型地面单位，建立路线与基础火力；让玩家看清效果并积累第一笔升级资金 |
| 5 | 第一压力检查：已解锁体型中的耐久单位，验证路线和集火 |
| 6—9 | 引入或混入快速、飞行等战术角色；一次只增加一种主要认知负担 |
| 10 | 第二压力检查：已有角色的组合，要求普通火力和范围火力分工 |
| 11—14 | 提升密度，加入本关允许的下一体型档；给玩家完善减速区和二次覆盖的机会 |
| 15 | 第三压力检查：重型或精英护卫组合 |
| 16—19 | 完整混编，考验火力覆盖与升级选择；调整角色组成形成操作窗口 |
| 20 | 压轴：一只本阶段允许体型的精英或首领加护卫；怪物总数继续增长 |

第 1 关压轴用强化后的现有小中型单位，不提前放巨人或超大首领。压力波之后通过角色组成调整形成缓冲，数量和总有效生命仍须继续增加。

时间配置首版：

```text
RoundData.interval = 0
EnemyList.interval = 0
Global.autoStartRoundDelayMs = 0        # 等玩家完成开局布防并点击开始
Global.autoNextRoundDelayMs = 5000      # 清场后5秒；允许现有按钮立即开下一波
```

保留“上一波清场后再开下一波”，首版不增加跨波重叠、提前开波奖金或多入口系统。这样最高单波 46 只，也不会因为常规波次叠加撞到 200 同屏上限。

1 倍速目标时长：第 1—5 关约 8—12 分钟，第 6—15 关约 10—15 分钟，第 16—20 关约 12—18 分钟。计时从点击第一波到胜负结算，包含波间自动等待，排除暂停和开场无限准备；不要直接用进关即开始的 GameClock.LevelElapsedSec 代替此验收口径。

出怪加固定等待本身的理论下界约为第 1 关 5 分 35 秒、第 20 关 9 分 15 秒，还需加每波末尾敌人的移动和击杀时间。上述时长是需要实测校准的目标。

## 三、数量与强度公式

设关卡等级 `L=1..20`、本关波号 `w=1..20`、`x=w-1`。

### 3.1 数量和密度

```text
N(L,w) = L + w + 6
spawnIntervalMs(L,w) = clamp(900 - 15*(w-1) - 5*(L-1), 450, 900)
```

因此：

- 第 1 关：8、9、10……27 只，总计 350 只。
- 第 20 关：27、28、29……46 只，总计 730 只。
- 同一关相邻波严格增加 1 只；相邻关的同波号也严格增加 1 只。
- N 是包括首领和飞行单位在内的总数。首领替换一只护卫，不额外少配普通怪，也不改变数量公式。

### 3.2 有效生命预算

护甲为百分比减伤，因此使用 `EHP = HP/(1-armor)` 评价耐久，而不只比较裸 HP。

```text
S(L) = 1 + 0.03*(L-1)
R(w) = 1 + 0.12*x + 0.018*x*x
P(w) = 1.12，若 w 为 5、10、15
       1.25，若 w 为 20
       1.00，其余

rawB(L,w) = N(L,w) * 30 * S(L) * R(w) * P(w)

B(L,w) = max(
    rawB(L,w),
    ceil(B(L,w-1)*1.04)，仅 w>1 时参与,
    ceil(B(L-1,w)*1.04)，仅 L>1 时参与
)
```

生成顺序固定为关卡从 1 到 20、每关波号从 1 到 20。B 为整波有效生命预算，不能再叠加一份关卡或波次 HP 倍率。

各角色按下表分配权重。权重用于分配整波预算，不能直接理解为固定 HP。

| 战术角色 | EHP 权重 q | 基础速度 格/秒 | 护甲 | 击杀金 | 漏怪扣血 |
|---|---:|---:|---:|---:|---:|
| 普通小怪 | 1.00 | 1.10 | 0 | 2 | 1 |
| 虫群杂兵 | 0.65 | 1.05 | 0 | 1 | 1 |
| 快速单位 | 0.85 | 1.60 | 0 | 2 | 1 |
| 飞行单位 | 1.20 | 1.40 | 0 | 3 | 1 |
| 中型常规 | 2.00 | 1.00 | 0.08 | 3 | 1 |
| 重型单位 | 4.00 | 0.80 | 0.18 | 5 | 2 |
| 精英单位 | 7.00 | 0.75 | 0.22 | 8 | 2 |
| 大型首领 | 18.00 | 0.65 | 0.25 | 25 | 4 |

```text
Q = 本波所有个体的 q 之和 = Σ(角色数量 * 角色权重)
HP_i = B(L,w) * q_i/Q * (1-armor_i)
speed_i = 角色基础速度 * (1 + 0.002*(L-1) + 0.001*(w-1))
```

用 float 保存 HP，避免强行取整造成预算漂移。生成后从导出 JSON 重新计算实际 ΣEHP，误差控制在目标 B 的 0.5% 内，并验证相邻波、相邻关同波号严格增长。

护甲已经包含在预算换算中，不要再为它重复乘一次难度系数。重型更耐打主要依赖 q；现有三塔没有“高单发天然破甲”的机制。

本方案保证数量、整波有效生命和同角色基础速度成长；**不承诺每种资源的单只 HP 在所有编队变化中都单调**。若混编变化使同角色单体 HP 出现明显下降，优先平滑角色占比或微调预算，并在逐波报告说明。不要把这个现象隐藏成“所有属性都逐波增长”。

### 7.2 首版五星时间基准

先从最终波次配置生成可复算的初始门槛，再用合法参考布防校准：

```text
A_w = 本波最后一只怪的计划出生时间 - 第一只怪的计划出生时间
    = (N(L,w)-1) * spawnIntervalMs(L,w)     # 本方案两个开始延迟均为0，单位ms
tailBudgetMs(d) = 10000 + 2000*(d-1)
Par0(L) = 5000 * ceil( Σ_w(A_w + tailBudgetMs(d)) / 5000 )
parCombatTimeMs(L) = 经参考策略验证后固化的 Par0 或校准值
```

第 1 关初始 Par0=440000ms（7分20秒战斗时间）；第 20 关初始 Par0=825000ms（13分45秒战斗时间）。这些数值不包括开场和波间布防等待，与前文整局时长口径不同。

Par0 只是可执行的校准起点，不能据此宣称满星已经可达。每关须提供可复现的五星布防轨迹及其击杀、经济、路径覆盖和时间证据；地图、敌人 HP/速度/组成、塔属性、收益任一改变，都要重新校验该关门槛，更新 planHash，并在报告说明调整依据。不要仅为了让一个低效布局拿五星而无限放宽 Par。

planHash 应由 profileId/profileRevision、最终怪物数值、编组及间隔、地图 cells、塔属性、经济和评分参数的确定性序列化生成；不包含 planHash 自身。每个 levelId 的成绩归属和比较统一使用完整评级版本键 `(profileId, balanceRevision, ratingRevision, planHash)`；下文“同评分版本”均指此完整键一致。正式内容发生影响可比性的改变后，新成绩与旧成绩分开归档，已获通关与解锁保留；只在编辑器预览或切换草稿预设时不执行正式存档迁移。开始本局时冻结本局配置和 Par，不随玩家布塔后的路径、当前余额、历史星数或切换倍速动态改变。

### 7.3 评星条件：从高到低取最高满足档

所有正式胜利先通过完整性检查：HP>0、maxHp>0、完成本关全部正式波次、实际成功出生数等于配置计划总数、击杀数＋漏怪数等于实际出生数，无调试强制胜利、跳波、资源失败或无效评分证据。

| 星级 | 必须同时满足的条件 |
|---|---|
| 5 星 | 正式完整通关；满血；总漏怪=0；全部计划怪物均击杀；战斗模拟用时 T≤Par |
| 4 星 | 正式完整通关；剩余生命≥90%；总漏怪≤2；精英和首领漏怪=0；T≤1.25×Par |
| 3 星 | 正式完整通关；剩余生命≥75%；首领漏怪=0 |
| 2 星 | 正式完整通关；剩余生命≥50% |
| 1 星 | 其余正式完整通关且 HP>0 |
| 0 星 | 防御失败、未完成正式关卡；调试或完整性无效的结果不写入正式成绩 |

初始 20 血时，生命门槛分别为 20、18、15、10、至少 1。首领漏掉即最高 2 星；精英漏掉即最高 3 星。首领及精英身份根据生成后的角色集合判断：Type=5 应与首领集合一致，但不能把全部 Type=3 重型误当作精英，也不能根据漏怪扣血量猜身份。

比例用整数交叉相乘，门槛包含等号：例如 `1000*hp >= 900*maxHp`；四星时间用 `4*T <= 5*Par`，中间运算使用足够宽的整数。本方案完整 20 波的战斗时间必须大于 0 且计时有效标记为真。maxHp≤0、时间≤0、关键统计缺失或版本不符属于无效证据，不回退成“自动一星”，也不能把新字段缺省值 0 当成超快通关。

建立唯一评分入口，例如 `LevelRatingEvaluator.Evaluate(profile, runMetrics)`，返回星级、各条件是否满足、未达成原因、评分版本。正式结束、失败和调试预览复用同一口径；UI 不单独重算。只使用本局一份完整结算结果，不把历史最佳生命、历史最快时间和本次击杀拼成五星。

同评分版本的历史成绩只升不降；先读 previousBest，再写本局结果，结算分别展示“本次”和“历史”。较低星重玩不覆盖历史五星。记录该最佳星级对应的一局证据；独立的历史最快时间可以继续保留为纪录，但不用于拼接评星。

### 7.4 战斗计时、统计与有效成绩

增加独立 `combatElapsedMs`：每波从第一只怪**成功出生**开始，到全部计划怪物完成击杀/漏怪结算为止，累计全部波的模拟用时。波内刷怪间隔和追击尾部计入；开场准备、波间 5 秒、波间额外布防等待、暂停、Loading、结算、后台及离线时间不计入。玩家可从容布防；半波退出时，进度、收益、消耗、统计和时间一起回退到波次检查点，不能在保留半波收益或进度时只回退计时。

整局节奏报告另记 `levelElapsedMs`，从点击第一波到最终结算，包含所有波间等待但排除暂停与离线。两种时钟在字段名、UI 文案与最佳时间记录中区分，不能拿旧 bestTimeMs 当成新战斗评分时间。

GameClock.Tick 与 DeltaTime getter 必须共用按帧幂等的刷新入口，同帧缓存和计时只更新一次；修复当前 Tick 填缓存却漏掉时间累加的问题。评分时钟消费统一模拟 dt，1×/2×/3×不直接使用墙钟时间；暂停和后台冻结。使用未四舍五入的累加器，结算时统一换毫秒，不能每帧取整后累计。快照保存原始高精度累加器，或整数毫秒与小数余量，采用可往返恢复的序列化；不能在每次存盘时截掉余量，造成反复继续游戏少计用时。

本局至少采集：runId、profileId/profileRevision、版本/planHash、expectedWaveCount、completedWaveCount、expectedEnemyCount、successfulSpawned、killed、leaked、bossLeaked、criticalLeaked、hp/maxHp、combatElapsedMs、levelElapsedMs、debugOverride，以及逐波计数和用时。监听 EnemyKilledEvent / EnemyReachedEndEvent 时在对象回收前读取配置，保证每只敌人仅结算一次；当前漏怪事件在扣 HP 前发出，不要在事件回调中提前生成最终评分。

修复 `WaveManager` 调 Spawn 后无论成败都推进游标的问题：同屏上限导致出生暂缓时，保留待刷项并退出本帧循环，不能死循环；非法资源、配置或路径应阻止开局或明确终止本局正式评级，不能吞怪后提前通关。第一组 WaveStartEvent 当前不会触发，完整波数统计不能仅靠它累计。

F2 强制胜利、编辑器跳游标等标为调试结果，仅用于界面预览，不写星级、解锁、通关次数、最佳用时或正式挑战证据。FinishRound、ShowClearPopup 与胜利事件共享一次性结算结果，防止重复 RecordClear 或重复奖励。

### 7.5 把高星可达性作为数值设计验收

同一套地图和敌群应允许：基础合法布局完成 1—2 星；合理的普通＋火力＋减速布局达到 3 星；优化路径、关键塔位和升级顺序达到 4 星；完整守住且清场效率达标达到 5 星。不要把战术组合、固定布局或“必须建三种塔”硬编码为评分条件，评分看防守结果和效率。

第 5、10、15、20 波承担检查作用。逐波报告重点列出这些波的漏怪身份、实际塔火力、清场战斗用时及对最终星级的影响。高星应促使玩家优化覆盖和升级，不依赖永久数值、付费或随机好局。

至少为每关提交一套五星参考方案及一套有明确失误、只能得到较低星的对照。离线仿真只能标预测；未实玩校准的 Par 与五星可达性标为待验证，不能写“已完成平衡”。若普遍只能通关一星或无脑任意布塔即可五星，应联动调整怪物、塔、收益、地图和 Par。

## 八、八档数值预设与自定义调整

### 8.1 八档首版参数

八档应是真正影响生成结果的配置，不能只是下拉框标签。采用稳定 ID，允许以后追加预设；首版 D04“中等”为默认，所有倍率为 1，精确复现前文基准。

| ID | 数值预设 | 整波 EHP 倍率 | 速度倍率 | 出怪间隔倍率 | 初始金币倍率 |
|---|---|---:|---:|---:|---:|
| D01 | 非常容易 | 0.50 | 0.90 | 1.10 | 1.40 |
| D02 | 容易 | 0.65 | 0.94 | 1.07 | 1.25 |
| D03 | 中等偏下 | 0.82 | 0.97 | 1.04 | 1.10 |
| D04 | 中等 | 1.00 | 1.00 | 1.00 | 1.00 |
| D05 | 中等偏上 | 1.18 | 1.02 | 0.98 | 0.96 |
| D06 | 困难 | 1.40 | 1.04 | 0.95 | 0.92 |
| D07 | 非常困难 | 1.65 | 1.06 | 0.92 | 0.88 |
| D08 | 极度困难 | 1.95 | 1.08 | 0.89 | 0.84 |

这些倍率是待校准的首版，不表示八档都已验证可通关。先固定怪物数量、首次体型/机制登场、护甲、漏怪扣血、塔属性与价格、击杀金、清场奖和 20 点初始生命，以较少变量建立清晰梯度。非常容易仍保留完整 20 波和必要机制；极度困难也必须有合法可复现的通关和五星方案，不能靠无限 HP 或不可防御的飞行单位制造无解局。

```text
N_profile(L,w) = L+w+6                         # 八档均不缩放数量，维持严格递增
B_profile(L,w) = B_base(L,w) * ehpMultiplier   # B_base 先按第三节递推一次
speed_profile = speed_base * speedMultiplier
gap_profileMs = clamp(roundHalfUp(gap_baseMs*gapMultiplier), 350, 1100)
gold_profile(L) = max(1, roundHalfUp((100+18*(L-1))*goldMultiplier))
HP_i = B_profile(L,w) * q_i/Q * (1-armor_i)
```

`roundHalfUp` 对此处正数按 `floor(v+0.5)` 定义，编辑器与命令行一致。倍率从原始基准重算，不能读上次导出值再次相乘；EHP 只在整波预算层缩放一次，不再给单体 HP 叠乘。八档均为 20 关×20 波，每个候选集 400 波，共 3200 波验证样本；实际应用只输出所选预设的 400 波，不扩成 160 个玩家关卡。

第一关初始金币依次为 140、125、110、100、96、92、88、84；第一波 EHP 依次为 120、156、196.8、240、283.2、336、396、468。工作台应显示这些可核验结果。八档相同关/波的 EHP、速度从易到难不下降，间隔和开局金不增加；这只是参数梯度，实际难度顺序仍须用策略结果验证。

### 8.2 预设与五星、阶段、版本的关系

Stage I—V 决定战役内成长和角色投放，profileId 决定本次全战役数值倾向；两者共同生成最终配置。界面示例：“第 10 关 / 战役阶段 III / 调参预设 困难 / 预测成绩 4 星”。玩家界面至少展示实际应用的难度名称；无需在首版增加八套选择流程。

八档使用相同 1—5 星生命、漏怪和关键怪规则，每关均可得五星。每档按自己的最终 gap、数量和地图重算 `A_w`、Par0，再独立校准 Par；不能简单用 EHP 倍率乘旧 Par。第七节给出的 440000ms、825000ms 仅是 D04 的初始值。未校准预设显示“时间基准待验证”，不得标为平衡完成。

LevelRating 正式源表仍为所选预设的 20 行，加入 profileId/profileRevision；其它预设的候选配置与报告放在暂存目录。TotalStars 统计当前正式预设及评级版本的 20 关，仍为 100 星上限，不把八份成绩累加成 800。调试预设不影响正式解锁；若以后增加玩家可选难度，必须另做按 levelId+profileId 分档的进度、快照和 UI，本轮不隐式加入。

### 8.3 自定义参数、覆盖优先级与数据所有权

新增权威生成配方 `Luban/BalanceDesign/balance_design.json`（待实现）：集中保存基准公式输入、角色模板、八档预设、当前待应用预设、精确覆盖项及版本。已有 Luban Excel 继续作为实际导出的运行数据源；生成器只维护 manifest 声明拥有的字段，其余现有字段保留。配方记录“如何生成”，Excel/JSON 记录生成结果，不能让两处都独立维护同一个公式参数。

工作台与命令行调用同一生成和验证核心；禁止在 EditorWindow、Python 脚本、运行时各写一份成长公式。可采用 C# 的纯数据计划生成器输出 resolved-plan，再由现有风格的 Excel 写入脚本消费；脚本只负责保留格式并落表，不重新实现公式。具体拆分可调整，但必须通过同输入、同输出的交叉检查。

允许编辑全局、单关、连续波段和单波；允许调整数量、角色比例、HP/EHP、速度、间隔、初始金、奖励、塔攻击/CD/范围/减速/价格、地图以及 Par。单位、合法值和影响范围必须明确，当前整数字段不能悄悄接受并丢弃小数。数量或 EHP 调整后仍须满足原严格递增约束，冲突时明确列出关/波并阻止应用，不能靠减少实际出生数或隐藏修正蒙混通过。

计算顺序固定为：原始基准→所选预设倍率→全局覆盖→单关覆盖→波段覆盖→单波覆盖→派生量和一致性校验。覆盖项区分“最终值替换”和“增量倍率”，相同优先级出现重叠写入时报错；记录来源、作用域和最终值。改塔攻击或 CD 后自动重算 DPS，改价格后重算累计投入/卖价，改数量后重建具体名单与总预算。HP 与 EHP 不能成为同一对象的两份独立目标；指定单体 HP 时回算实际 EHP 并检查整波预算，冲突需明确处理，不能后台重分配后让用户输入失效。

任何影响战斗效率或评分可比性的变更，包括怪物 HP、速度、组成/数量、间隔、地图、塔属性/价格、初始金、收益和评分参数，都使受影响关卡的 Par 校准状态失效；校准证据绑定最终 planHash。界面区分可重新计算的 Par0 与经证据验证的 Par，不能改完塔攻击或初始金后仍把旧门槛显示为已校准。

编辑现有预设后显示“已自定义”，允许另存具备稳定 ID 的新预设；不可静默覆盖内置八档或在每次开窗时恢复默认并丢掉修改。权威配方与显式覆盖项纳入版本控制、备份和回滚；临时草稿只用于恢复编辑，不进入运行时加载。直接手改受生成器管理的 Excel 字段时，应用前显示冲突，提供导入为覆盖项或放弃该候选的处理，不能下次生成时无提示覆盖。

### 9.3 三层快速验证

第一层为 EditMode 静态与数学检查：直接从候选计划检查引用、400 波名单、数量/EHP 单调、八档梯度、成本/收益、S/E/BFS、体型解锁、资源、评分参数和版本；不加载整场景或生成上千个 GameObject。候选无效时可继续编辑，但不能应用正式内容。

第二层为可重复离线策略模拟：消费同一 resolved-plan 和实际地图，按固定模拟步长运行合法坐标、建造/升级/卖塔时间表及实时余额；覆盖四方向路径变化、飞行直线、索敌、射击间隔、过量伤害、AOE 实际命中与最强减速。优先复用可脱离场景的逻辑；无法一致的部分逐项标为近似，报告模拟器版本、种子和误差范围，不把理论 DPS 推算伪装成游戏模拟。用唯一评分器生成预测结果。

内置或提供普通塔为主、火力聚怪、减速混合至少三类可复现策略模板，分别记录基础、合理和优化布防；策略失败、超时、路径不合法或余额不足时明确报告，不能自动补钱继续。支持一次跑单关、代表关或 8×20 关，支持单关/整批超时、取消和失败后继续。每个结果标注 profileId、levelId、planHash、策略 ID/版本、步长、模拟覆盖范围及统计。

第三层为真实 PlayMode 验证：经授权使用实际 WaveManager、塔、敌人、寻路、GameClock 和唯一评分器，至少对所选正式预设第 1/5/10/15/20 关进行合法完整回放，并比较离线预测；八档的代表关按第十二节扩展。单波压力测试允许设置试验余额/塔位，结果只能定位问题；证明通关或五星必须从该关合法初始状态连续完成全部 20 波，不能跳到最后一波或复用前一关资产。

所有预览、临时覆盖、跳波、策略自动回放均使用独立测试存储或内存存储。复用正式评分算法，但只显示“测试/预测评分”，不写正式星级、解锁、通关次数、最佳时间或正式局内快照。运行间清理事件订阅、对象池状态、时钟和测试存档，避免批测串局。测试入口不可默认出现在发行版。

### 9.4 应用、重载与回滚

预览仅在内存或 `Library/BalanceWorkbench/<jobId>/` 生成候选；窗口草稿可保存在同类本地目录并可显式导出。权威配方、源 Excel、Assets/Gen、Assets/ConfigJson 和正式存档不因预览而改变。应用前检查 Excel 文件锁、源文件哈希和外部修改，列出本批影响；备份配方、受影响源表、稳定 ID manifest、相关生成文件及版本。

先将配方解析为完整候选→在暂存区写候选 Excel→暂存 Luban 导出→解析并全量验证→校验源文件仍未变化→按事务日志应用。只有验证通过的候选能进入正式目录；保留 `.meta`、`FTProject.Gen.asmdef` 及其 `.meta`，只更新确有变化的生成文件。阶段失败或重载中断能恢复到一致版本，不能留下“Excel 新、JSON 旧”并显示成功。回滚恢复同一批源表、配方、manifest、生成数据和版本，检测备份后新增的外部修改，再刷新/编译并回读验证。

当前 Configs.LoadAsync 在 IsLoaded 时直接返回，EnemyConfig/TowerConfig/LevelConfig 持有已解析对象；仅重新导出或 AssetDatabase 刷新不会使当前局生效。首版以“新局读取新配置”为安全边界；编辑器专用重载只在无活动正式对局时加载完整候选、校验后原子替换，并清理相关资源/索引缓存。当前局冻结配置、Par 和 hash；不得在战斗中修改共享 cfg、重置漏怪或刷新计时来热调。使用资源包的加载模式还须重建/刷新实际 config 包，验证读取的版本/hash，而非只检查磁盘 JSON 时间。

“一键生成并重测”在未授权 Play Mode 时完成到编辑器静态检查并报告剩余步骤；已有播放授权时按其范围执行。单次输入、切换预设或窗口重开不得擅自改变播放状态，也不应每次弹确认打断普通草稿编辑。

### 9.5 响应、取消与跨重载恢复

长计算分帧或在纯数据后台任务执行，Unity API 只在主线程。Python/Luban 使用异步进程与每帧轮询，stdout/stderr 异步收集，禁止编辑器主线程 WaitForExit 忙等。显示任务 jobId、真实阶段、关/波、完成数、耗时、错误定位和取消按钮。先检测并说明本机 Excel 写入依赖及命令，不写死另一机器的 Python 路径；依赖缺失时保留草稿并给出可执行修复步骤。

编译/导入期间禁用冲突写入，采用任务互斥防止双击或两个窗口并发落表。取消仅终止本任务拥有的子进程并在安全边界结束，提交阶段不可中途留下半批内容；其它进程、Unity 编辑器和用户资源不被误清理。jobId、阶段、源/候选哈希、应用/备份记录跨域重载保留，恢复前重新核对，不能盲目重复已经提交的写入或奖励。

## 十、地图适配

先审计 20 张实际 cells，优先保留开阔布塔、由塔塑造路径的核心体验。地图是否调整，以有效射击时间、可建格、空地火力分工和通关证据判断，不以“障碍更多所以更难”判断。

- 第 1 关现为 11×5，其余多为 16/17×9。若第 1 关容不下清晰教学和基础路线，可以扩至约 13×7，并检查相机、触摸和 HUD 遮挡；无需为了改样式重写地图系统。
- 第 2—5 关保留宽松建造空间；第 6—10 关可增加稀疏交错障碍或禁建格；第 11—20 关围绕多个有效火力区设计，保持至少两种可行布防思路。
- 每图严格 1 个 S、1 个 E，四方向 BFS 连通。不可布塔封死路径，保留当前合法放置检查。
- 飞行仍直线移动，不因地面迷宫变长而延长受击路径。单独验证其 S→E 直线与对空塔覆盖。

- 更新 LevelMap、SceneInfo 的描述，使其与实际 cells 一致；必要时补充本地化。

首版不加入多出生口、地形伤害、可破坏障碍或新塔种；现有地图和刷怪架构没有直接提供这些机制。

## 十一、落地方式与数据管线

### 11.1 采用配置变体承载成长

当前 `EnemyManager.Spawn` 只接受 enemyId，`BaseEnemy.Init` 直接读取配置；减速恢复也回读 Config.Speed。首选生成**明确的 EnemyData 数值变体**，而不是修改共享配置对象或新增一套临时运行时倍率。

- 保留现有 1—132 原型 ID；新变体从检查无冲突后的 100000 起分配。
- 稳定键使用 `(profileId, levelId, waveOrdinal, canonicalEnemyId, role)`；用生成 manifest 固定 ID 映射，重复运行和来回切预设不会重复加行或更换已有 ID。候选集可共享资源，正式源表只应用选定预设所需的数值变体。

SQLite 是主后端，JSON 是降级后端，均要实现新字段的保存、读取与规范化。SQLite 的 SELECT/INSERT 是显式字段，新增字段不能只写在 SaveData C# 类里；可以将完整评分统计序列化为受保护列，与原波次快照同一次事务写入，并确保 runId/cursor 一致。旧星级、生命和用时是加密 TEXT，迁移经 C# 解密和重新写入，不能直接对密文做 SQL 数值运算。

SaveSchema 当前版本为 2，SaveData.CurrentVersion 当前为 1，是两套不同的版本体系。只有完成 SQLite 增量迁移与 JSON 显式兼容迁移后才能提升相应格式版本；必须替换 JSON 当前“version 不同就返回新档”的处理。测试两后端的 4/5 星写入、重启回读、旧档迁移与新快照恢复。
